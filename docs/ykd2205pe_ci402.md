# YKD2205PE EtherCAT 驱动器速查

研控 (www.yankong.com) EtherCAT 总线型步进驱动器。CoE + CiA 402。
开环步进(适配 42 两相开环电机)；电源 DC 24~50 V；**最大输出电流 2 A**；100BASE-TX。
通信模式: **SM 同步** 与 **DC 同步** (同步周期 250µs~4000µs) 都支持。
SM0/SM1 = 邮箱收发、SM2 = RxPDO、SM3 = TxPDO。站号由拨码 SW1~6 设定 (0~63)，
驱动器上电时写入 ESC 别名寄存器 0012h。

**注意**: 拨码站号对 **pysoem** 不可见 —— CoE 0012h 对象实测缺失 (SDO
"object does not exist")，pysoem 封装的旧版 SOEM 也不暴露 ESC 别名寄存器。
因此本框架(python 链) **按 EtherCAT 总线线序 (从站 0/1) 定位轴**。

> 若要真正按手册读取该 0012h 别名寄存器，须用原生 SOEM：见下文
> 「读取拨码站号」，工具 = [`aliasinfo/`](../aliasinfo/)。
> (手册 V2.4 另有 **2215h 从站节点来源** / **2216h 从站节点号** 可以改这个别名，
> 但那是写操作，本仓库不用。)

## 读取拨码站号 (原生 SOEM)

拨码站号存于每台从站 ESC 的 *Configured Station Alias* 寄存器 **0012h-0013h**
(由 SW1~6 在驱动器上电时写入)，普通 EtherCAT 主站启动时就靠读它识别/寻址。
python 链 (pysoem) 读不到这个寄存器，所以仓库里放了一个原生 SOEM 读取器工具
[aliasinfo](../aliasinfo/aliasinfo.c) (自有顶层工程，引用下载的 SOEM)：SOEM 在
`ecx_config_init()` 里已对每台从站 FPRD 0x0012，结果在 `ctx.slavelist[i].aliasadr`，
该工具只把它打印出来 (只读、不进 OP)。

构建并运行 (需要 VS/CMake；在仓库根配置顶层工程，`SOEM` 作为子工程):

```bash
cmake -S . -B build                 # 首次/改 CMakeLists 后重跑一次
cmake --build build --config Release --target aliasinfo
build/aliasinfo/Release/aliasinfo.exe '\Device\NPF_{GUID}'
```

输出形如 (位置 = 0-based 总线线序，与 python 链 `--pos` 一致):

```
2 台从站。位置为 0-based 总线线序 (主站起数)。
  位置    序号   配置地址     别名0012h      厂商ID      产品码  名称
  -----  -----  ------  ------------  ----------  ----------  ----
    0       1   0x0001        5 (0x0005)  0x00000994  0x00003000  YKD2205PE
    1       2   0x0002       17 (0x0011)  0x00000994  0x00003000  YKD2205PE
```

注意:
- 别名 = 0 表示拨码=0 或未启用，同型号多台仍按总线位置区分。
- 拨码站号是驱动器**上电时**读的，改动拨码须断电重启才生效。
- 该工具用 Npcap 独占网卡，运行期间勿同时跑 python 链的 pysoem 脚本。

### 状态迁移 (V2.4 p9 / V1.0 p26)

| Bit6 | Bit5 | Bit3 | Bit2 | Bit1 | Bit0 | 状态 |
|---|---|---|---|---|---|---|
| 0 | X | 0 | 0 | 0 | 0 | **Not ready to switch on** |
| 1 | X | 0 | 0 | 0 | 0 | **Switch on disabled** |
| 0 | 1 | 0 | 0 | 0 | 1 | **Ready to switch on** |
| 0 | 1 | 0 | 0 | 1 | 1 | **Switched on** |
| 0 | 1 | 0 | 1 | 1 | 1 | **Operation enabled** |
| 0 | 0 | 0 | 1 | 1 | 1 | **Quick stop active** |
| 0 | X | 1 | 1 | 1 | 1 | **Fault reaction active** |
| 0 | X | 1 | 0 | 0 | 0 | **Fault** |

低 4 位因此就是 `0000 / 0001 / 0011 / 0111`，与上面「初始化步骤表」逐行对应。

> **`[实测]` 这段是当前调试卡住的地方，务必看**：两台上电后第一次读到的 6041h 是
> **0x0210** (bit4 Voltage enabled + bit9 Remote，低 4 位 = 0000 = 手册「步骤 0」态)。
> 随后程序写 6040h = **0x0000**，再读到的是 **0x0231** (bit0+bit4+bit5+bit9，
> 低 4 位 = **0001** = 手册「步骤 1」态，即 **Ready to switch on / 电机释放**)。
>
> 结论有两条，都对代码有直接影响：
> 1. **按手册，0000 和 0001 都是「电机释放」**(步骤 0 与步骤 1)，都不是故障。
>    把「6040h=0x0000 时必须读回低 4 位 0000」写成硬断言，
>    在一台**已经上电自检完成**的驱动器上必然失败 —— 那是断言期望值不对，
>    不是通信故障。要判「未使能且无故障」，正确的判据是
>    **`(6041h & 0x000C) == 0`** (bit2 = 未使能、bit3 = 无故障)，而不是低 4 位全 0。
> 2. 想确认「远程控制被允许」，看的是 **bit9**：0x0210 / 0x0231 的 bit9 都是 1
>    (Remote 有效)，所以这**不是**「驱动器不接受控制字」那一类问题。
>
> 另外注意 bit5 的行为与本机是否符合标准 CiA402 尚**未确认**：标准里从
> Ready to switch on 写 0x0000 (Disable voltage) 应迁到 Switch on disabled
> (bit6=1)，而实测仍停在 bit5=1/bit6=0。判状态时**以 bit2/bit3 为准**最稳。

> 代码里 `sw_name()` / 断言掩码用到的位: `0x0001` Ready to switch on、
> `0x0002` Switched on、`0x0004` Operation enabled、`0x0008` Fault、
> `0x0010` Voltage enabled、`0x0020` Quick stop、`0x0400` Target reached、
> `0x1000` Set-point acknowledge。**这些位手册都定义了**(旧版文档说「未定义 bit6」
> 是错的)，用它们判状态没有依据问题。

## PDO 映射 —— 三个口径互不相同，只能现场读

| 来源 | 生效的 RxPDO | 生效的 TxPDO | SM2 / SM3 长度 |
|---|---|---|---|
| 手册 V2.4 附录 3 (p78~79, YKD) | 只映射 **6040h**，其余 11 项未映射 | **全部未映射** | 手册未给 |
| 手册 V1.0 (p38~40) | 同上 | **全部未映射** | 手册未给 |
| ESI V2.5 `<RxPdo>/<TxPdo>` | 5 项: 6040h:16 / 607Ah:32 / 60FFh:32 / 60B8h:16 / 60FEh:01:32 = **16 B** | 12 项: 603Fh:16 / 6041h:16 / 6064h:32 / 60FDh:32 / 606Ch:32 / 60F4h:32 / 60B9h:16 / 60BAh~60BDh:32×4 / 6061h:8 = **39 B** | Outputs 16 / Inputs 39 |
| ESI V2.5 `<Dictionary>` 默认值 | 2 项: `60400010h` + `60600008h` = **3 B** | 2 项: `60410010h` + `60610008h` = **3 B** | (同上) |
| **[实测] 2026-09-15 `motor_test` 只读运行** | **1C12h = { 1601h }**，1601h 共 7 项 = **23 B** (见下) | **1C13h = { 1A00h }**，1A00h 共 3 项 = **10 B** | IOmap **输出 23 + 输入 10** |

**默认分配并非三份一致** —— 这句旧结论是错的。三份资料说的是「1C12h = { 1600h }」，
但 **[实测] 这台设备的 1C12h 指的是 `1601h`**，而 `1600h` 是同一台驱动器里另一张
**没有生效**的表。所以：

> **「读出映射内容」不够，必须先读出「哪个 PDO 生效」。**
> 照着 `1600h` 去读偏移、去补缺项，不会报任何错 —— 那张表里的字段齐不齐都与过程
> 数据无关，于是「映射看着没问题」和「控制字根本发不出去」可以同时成立，
> 而偏移证明还照样通过。写死的必须是**分配对象**里读出来的那个索引。

1C13h = { 1A00h }（与三份资料一致）；1C00h:01~04 = SM0~SM3 通讯类型 1/2/3/4。

**[实测] 2026-09-15 的完整实读值** (只读运行，一个字节都没写)：

```text
1C12h (分配): 1 项  0x1601
1601h (映射): 7 项
  [1] 6040h:00  16 bit  @ +0    控制字
  [2] 6060h:00   8 bit  @ +2    运行模式
  [3] 607Ah:00  32 bit  @ +3    目标位置 (CSP)
  [4] 60FFh:00  32 bit  @ +7    目标速度 (PV)
  [5] 6081h:00  32 bit  @ +11   轮廓速度 (PP)
  [6] 6083h:00  32 bit  @ +15   轮廓加速度
  [7] 6084h:00  32 bit  @ +19   轮廓减速度
  合计 184 bit = 23 字节      <-- 那 23 字节就是它, 已解释
1C13h (分配): 1 项  0x1A00
1A00h (映射): 3 项
  [1] 6041h:00  16 bit  @ +0    状态字
  [2] 6064h:00  32 bit  @ +2    实际位置
  [3] 606Ch:00  32 bit  @ +6    实际速度
  合计 80 bit = 10 字节
```

**读法**:
- **不要相信任何一份「出厂映射」**。同一个厂家在手册、ESI 声明、ESI 字典默认值里
  给了三种答案，真机上量到的又是第四种 —— 驱动器当前的映射很可能被厂家上位机
  改过。**每次运行前读一遍 `1C12h` / `1C13h`，按它们指到的索引再读那张映射表，
  再定偏移。**
- 三份资料唯一的共识是: **6040h 在 RxPDO 的第 0 项**，所以控制字在输出镜像的 `+0`
  字节 —— 这一条 [实测] 也成立。但 6041h 在 ESI 声明里位于 **输入镜像 +2**，
  [实测] 1A00h 里却在 **+0**：偏移必须从实读的映射表推，不能照抄任何文档。
- ~~实测输出 23 字节无法解释~~ —— **已解释**：那 23 字节**不是** `1600h`，而是
  `1601h`。6040h(2) + 6060h(1) + 607Ah(4) + 60FFh(4) + 6081h(4) + 6083h(4) +
  6084h(4) = 23。旧结论之所以「与任何一份文档的组合都对不上」，是因为当时假设
  生效的是 `1600h`。这是个**反例**：资料对不上时，先怀疑自己读错了对象，
  再怀疑设备不符合规范。
- 副作用：**当前生效的映射里 `6040h` / `607Ah` / `60FFh` 已经齐全**，所以做
  CSP / PV / HM **不需要改写任何 PDO 映射**。但**这不等于"什么都不用写"** ——
  见下一条，那是这份文档里代价最大的一个坑。
- **生效 RxPDO 里的每一项都是"主站拥有"的 —— 不驱动它，就是在每周期下发 0。**

  主站每周期把整块输出镜像原样发出去，驱动器控制环连续采样自己的 SM2 缓冲。
  所以表里每一项的主站侧都是**由我们决定**的：写了就是那个值，没写就是 **0**，
  而且不会有任何报错。`1601h` 有 7 项，`motor_api` 曾经只驱动其中 4 项。

  > **通用规则（与具体驱动器无关）：一个对象只要在生效的 RxPDO 里，就必须经过程
  > 数据驱动它；SDO 写会被下一帧覆盖。** 反过来，不在 RxPDO 里的对象才轮到 SDO。
  > 判断"在不在"只能实读映射表 —— 所以 `motor_api` 在 setup 时逐项实读偏移。
  >
  > 另一个容易踩的变体：**驱动器可能只接受在"未使能"状态下改运行模式**（CiA402 的
  > 要求）。经过程数据改也一样 —— 要先失能，再改 `6060h`，再使能。

  这一条在本仓库用**两次真机事故**换来的，两次都是"没写的那一项"：

  **① `6060h`（运行模式）在 `+2`。** [实测] 2026-09-15 的 S6：SDO 写 `6060h = 8`
  （CSP），回读 `6060h` 对象**确实是 8**，但 `6061h`（实际模式）一直读回 **0** ——
  因为主站每周期都在下发 `6060h = 0`，驱动器认的是过程数据那一侧。

  **② `6083h` / `6084h`（轮廓加减速度）在 `+15` / `+19`。** [实测] 2026-09-15 的
  PV 运行**全阶段 PASS、退出码 0，而电机一步没走**：

  ```text
  S4/S5/S6 → 停后:  6064h = 15270510   (全程一个计数都没变)
                    606Ch = 0          (全程)
  使能时 6041h = 0x1637,  跑的时候 = 0x0237   (bit12 "Speed=0" 被清零)
  ```

  `6041h` bit12 在 PV 下是 `Speed`（1 = 速度为 0），它**跟着我们下发的 `60FFh`
  变了** —— 说明驱动器确实收到了速度指令、也承认目标速度非零。但 `6083h = 0`
  意味着**斜坡永远起不来**：驱动器认为该转，实际减速器上不来，`606Ch` 停在 0，
  一步不走。驱动器自己的 `6083h/6084h` 是 **500000**（见 `baseline_ykd2205pe.ini`），
  被主站每周期下的 0 盖掉了。

  > 为什么这个坑比 ① 更难发现：**所有"驱动器接受了指令吗"的断言都会通过。**
  > bit12 清零是对的、模式切换成功是对的、没故障没限位都是对的 —— 没有一条在问
  > "电机动了吗"。判据只能是 `6064h`（实际位置）有没有变、`606Ch` 有没有非零。
  > `motor_api` 的 `em_pv_run_multi()` 现在会把这两项打出来，位置一个计数没变即判
  > **FAIL**。

- **`6081h` 是这条规则下唯一"有意不驱动"的一项**：它只在 PP 下当轮廓速度用，而
  PP 是 `slide_motion` 的活。主站下发 0 与驱动器基线（`6081h = 0`，表示"从未设过"）
  一致，所以无害 —— 但它是**明确交代过**的，不是漏掉的。判据是
  `em_dump_pdo()` 里那张「本接口对生效 RxPDO 每一项的处置」表：7 项逐项写清
  偏移与"驱动 / 不驱动"及理由。加字段时先看这张表还差谁。
- 顺带一个容易忽略的后果：**进 OP 的"只读"运行同样在覆盖这些项。**
  带 `--allow-pdo` 就会进 OP 并开始发帧，于是连"只读观测"那次也把
  `6081h`/`6083h`/`6084h` 推成了 0。所以 `motor_api` 的 pin 动作放在
  `em_setup()` 里、**进 OP 之前**。
- 这正是 `test2.c` / `sm_pdo.c` / `motor_api` 里「**偏移证不出就拒绝 (退出码 4)**」
  那条护栏的由来，别把它当成多余的严格。

> **对「空 TxPDO 挡 SAFE_OP」这条根因的修正**：
> 手册确实说 1A00h 出厂未映射，`[实测] 2026-09-11` 也确实拿到
> **AL 状态码 0x001E (Invalid input configuration)**、从站拒绝 PRE_OP→SAFE_OP；
> 但 `[实测] 2026-09-15` 的 test2 运行里 **1A00h 已含 6041h、SM3 = 10 字节，
> SAFE_OP 与 OP 都到达了**。所以「出厂空 TxPDO」是**手册口径**，
> 不是这台设备的当前状态 —— 报 0x001E 时要先去读 1A00h/1C13h 确认，
> 不要默认它就是空的。

## 数字输入 / 输出与限位

本机硬件 (V1.1 §1.2/§4.2.4): **4 路光电隔离输入 X0~X3** (5~24 V，共 XCOM，
**电平脉冲宽度需 > 10 ms**)、**2 路光耦隔离输出 Y0/Y1**。

- **2004h** (U16 RO): 输入端子电平 **Bit0~Bit3 = X0~X3** (物理状态，常开/常闭由 2300h 决定)。
- **2005h** (U16 RO): 输出端子状态 **Bit0~Bit1 = Y0~Y1**。
- **2300h / 2301h** (U16 RW, 默认 0): 输入/输出端子**有效电平逻辑**，对应位 0 = 常开、1 = 常闭。
- **2310h~2313h / 2320h~2321h / 2330h~2333h**: 端子功能与滤波，见下表。
- **60FDh** (U32 RO) 是**经过 2300h 电平反转与 2310h 功能映射之后**的结果：

| 位 | 含义 |
|---|---|
| Bit0 | 负限位 |
| Bit1 | 正限位 |
| Bit2 | 原点开关 |
| Bit3~Bit15 | 保留 |
| Bit16 / Bit17 | 探针 1 / 探针 2 |
| Bit18~Bit22 | 用户自定义 0~4 |
| (Bit31) | Z 信号 —— 该位只在 V2.4 的 **MS-Mini3E/S3E 附录**里写明；YKD 表未列 |

## 设备导入验证工具 slide_verify (原生 SOEM)

滑台设备接入/上电 EtherCAT 总线时的**导入验证**:扫描总线 → 逐台读取身份与关键
CiA402 对象 → 判定是否为受支持的 YKD2205PE 滑台驱动器,逐项给出 PASS / WARN /
FAIL,最后汇总并返回退出码。**只读工具**:不进 OP、不写 6040h 控制字、不做使能
序列、不动电机。验证深度:PRE_OP 读对象(主),随后可选尝试 SAFE_OP(失败记
WARN 不致命)。

**源码位置与工程结构**(本仓库自有代码,独立于下载的 SOEM):

```text
EC_CPP/
├─ CMakeLists.txt        # 顶层工程: add_subdirectory(SOEM) + add_subdirectory(slide_verify)
├─ slide_verify/         # 本工具 (slide_verify.c + CMakeLists.txt)
└─ SOEM/                 # 下载的第三方库, 未改动
```

构建(在仓库根,顶层工程会引用并编译 SOEM 库,但不构建 SOEM 自带 samples):

```bash

cmake --build build --config Release --target slide_verify
build/slide_verify/Release/slide_verify.exe '\Device\NPF_{GUID}'
```

不带 `ifname` 时仅列出可用网卡。

**识别集合**(与代码 `sv_is_ykd_slave()` 一致):厂商 `0x0994`,产品码
{`0x2000`, `0x3000`} 双收。位置 = 0-based 总线线序(与 python 链 `--pos`、aliasinfo
一致)。

**输出流程**:
1. 身份表(位置 / 序号 / 配置地址 / 别名0012h / 厂商ID / 产品码 / 修订 / 序列号 / 状态 / 名称);
2. 逐台身份判定(是否 YKD、是否达 PRE_OP);
3. 每台 YKD 的 PRE_OP **对象级验证**(逐对象 PASS/WARN/FAIL + 读数:状态字低4位/
   Fault位 bit3/到位 bit10、操作模式名 1/3/6/8、实际位置/速度等);
4. 可选 **SAFE_OP 探针**(进不去记 WARN 不致命;默认空 TxPDO 是正常诱因);
5. 汇总表 + 退出码。

**对象校验矩阵**(表驱动 `sv_objs[]`,加对象只改表不动码):

| 对象 | 角色 | 判定 |
|---|---|---|
| 6041h 状态字 / 6060h / 6061h / 6064h / 606Ch | **必需** | 缺失或超时 → FAIL;Fault 位=1 / 未知模式 / PRE_OP 下仍有速度 → WARN |
| 607Ah / 6081h / 6083h / 6084h / 60FDh / 60FEh | **可选** | 缺失 → WARN;读出仅显示 |

**退出码**:

| 码 | 含义 |
|---|---|
| 0 | 通过:至少 1 台 YKD 且全部 PASS |
| 1 | 用法错误 / 初始化失败(网卡打不开、Npcap 被独占、需管理员) |
| 2 | 空总线(config_init 未发现从站) |
| 3 | 存在 YKD FAIL(必需对象缺失/超时、YKD 未达 PRE_OP) |
| 4 | 无 FAIL 但含 WARN(可选对象缺失、未达 SAFE_OP、未知模式、混挂非 YKD) |
| 5 | 有从站但一台 YKD 都没有(环境不匹配) |

> 想干净退出 0,就只在总线上挂 YKD2205PE 且必需对象全部可读。别名=0 不判 FAIL,
> 同型号多台按总线位置区分。

**注意**:与 aliasinfo / python 链 pysoem 一样独占 Npcap 网卡,勿同时运行
(docs 顶部的网卡独占提醒同样适用)。

## 带动作验收验证工具 slide_motion (原生 SOEM)

`slide_verify` 证明的是「驱动器能被识别、能读」。它**刻意**不进 OP、不写 6040h、
不动电机, 所以参数错、电子齿轮错、电机相序反、编码器方向反、限位接反这些故障
在它眼里全是 PASS —— 只有让轴真的动一次才暴露。

`slide_motion` 就补这一段:参数基线与漂移比对 → CiA402 使能状态机 →
相对微动并校验编码器反馈的行程/方向/闭环归位。

**默认不动**:不给 `--allow-motion` 时全程只读, 一个字节都不写; 移动还额外需要
`--allow-jog` 与一次交互确认。它走 **SDO + PRE_OP/SAFE_OP**, 不开 OP、不改 PDO
映射 —— 因为 PP 模式的速度规划器本来就在驱动器内部, 不需要周期数据。

阶段:`S0` 身份门(只读) → `S1` 参数基线(只读) → `S2` OP/DC(**本版未实现**)
→ `S3` 使能状态机 → `S4` 微动与反馈闭环 → `S5` 收尾(无条件执行)。

> 退出码与 `slide_verify` 不同, 且多一个 **10**: 收尾后回读 `6041h` 仍报
> Operation enabled, 即**电机可能仍带电** —— 它覆盖其它所有码。

**完整设计、安全须知、微动判据、退出码与真机实测记录**:
[docs/slide_motion_verify.md](slide_motion_verify.md)。

示例基线:[baseline_ykd2205pe.ini](../baseline_ykd2205pe.ini)。

> **关于 2401h 最大电流**:上表记的 2000 mA **就是 YKD2205PE 的正常出厂值**
> (机型上限 2 A；手册默认列写的是型号相关的 2000/4000/5500)。基线文件仍然
> 有价值 —— 它固定的是**这台设备的总线位置与整定值**, 不只是手册默认值。
>
> **关于 2201h**:基线目前没有记录这个对象, 而它决定行程当量来自 2400h (细分)
> 还是 2408h/2409h (电子齿轮)。**建议在基线里补一条 2201h**, 否则「1 脉冲 = 多少
> 位移」这个前提没有被任何断言固定住。

## 状态机切换专项验证小程序 sm_state / sm_pdo (原生 SOEM)

`slide_motion` 的 S3 用的是 **SDO + PRE_OP/SAFE_OP**, 实测在出厂配置下到不了 ——
TiPDO 未映射时从站会以 AL `0x001E` 拒绝 `PRE_OP → SAFE_OP`, 而 PRE_OP 下 CiA402
状态机根本不响应 `6040h` (论证与实测见
[slide_motion_verify.md](slide_motion_verify.md) §6)。这两个小程序专门把这件事单独
拎出来验:

| | `sm_state` | `sm_pdo` |
|---|---|---|
| 控制字怎么发 | **SDO** 写 `6040h` | **RxPDO 过程数据**里的 `6040h` |
| 状态字怎么读 | SDO 读 `6041h` | **TxPDO 过程数据**里的 `6041h` (+ 步末 SDO 交叉核对) |
| AL 状态 | PRE_OP / SAFE_OP | SAFE_OP / **OP** |
| 写 PDO 映射 | 不写 | **写** `1A00h`/`1C13h` (仅 RAM, 默认还原) |
| 需要授权 | 无 (只写 `6040h`) | `--allow-pdo` |

两者的切换序列完全同构 —— 上行 `0x0000 → 0x0006 → 0x0007 → 0x000F`,
`--hold` 观察, 下行 `0x0007 → 0x0006 → 0x0000`。断言掩码都是 **`0x000F`**
(只取低 4 位)。**两者都不发运动指令**, 不写 `607Ah`/`6060h`/软限位;
但第 3 步之后电机通电有保持力矩。

> **掩码 `0x000F` 的现状 (据手册更正)**：手册**定义了** bit5/bit6, 低 4 位就是
> `0000/0001/0011/0111` 四态。掩码取低 4 位本身没问题, 但**第 0 步「期望 0x0000」
> 是错的**: 上电自检完成后驱动器处于 `0001` (Ready to switch on, **电机释放**),
> 而手册的「步骤 0 = 0000」只在刚上电那一瞬成立。
> 要判「未使能且无故障」请用 **`(sw & 0x000C) == 0`** (bit2 未使能 / bit3 无故障)。
> 详见上文「状态字 6041h」里的实测段。

### sm_pdo 为什么必须写 PDO 映射

手册口径的出厂 `1A00h` (TxPDO0) 是**未映射**的 → SM3 长度为 0 → 从站拒绝 SAFE_OP
(AL `0x001E`)。要验证 PDO 路径, 这个前置条件绕不过去。边界收在:

- 只写 **RAM**, **从不写 `2102h`** (EEPROM) —— 掉电即回出厂映射。
- 默认跑完**还原**成运行前快照; `--keep-mapping` 才保留; `--no-map` 整个跳过
  (此时若映射不合期望, 直接以退出码 4 拒绝)。
- 默认只往 TxPDO **追加 `6041h`** 一项, 已有映射项原样保留。
- **偏移证不出就拒绝** (退出码 4): `6040h`/`6041h` 在过程数据镜像里的字节偏移
  必须能从映射表严格推出; 不猜。写错字段可能凭空下位指令。
- `6040h` **不经 SDO 写** —— 它就是被测变量。唯一的 SDO 写入口只用于映射对象与
  `--reset-fault` 的故障复位。

```
sm_pdo [网卡] [选项]
  --allow-pdo           允许写 PDO 映射并进 OP。不加则只读快照 (退出码 0)。
  --axis N              选哪根轴 (总线位置, 0 起)。默认第一台 YKD2205PE。
  --no-map              不写 PDO 映射 (要求映射已合法, 否则退出码 4)。
  --keep-mapping        跑完保留改过的映射 (默认还原)。
  --state op|safe-op    跑到哪一级 AL 状态, 默认 op。
  --dc                  配置分布式时钟 (自由运行进不去 OP 时试它)。
  --cycle US            DC 同步周期, 默认 1000 (范围 250~4000)。
  --reset-fault         允许清故障 (进 OP 后经 PDO 推 0x0080)。
  --allow-other-slaves  总线上还有别的从站时也继续 (它们留在 PRE_OP)。
  --hold MS             停在 Operation enabled 的观察时长, 默认 500。
  --tmo MS              单步等待超时, 默认 1000。
  --ifname=GUID         覆盖写死的网卡。
```

退出码: **0** 全 PASS / **1** 用法或初始化失败 / **2** 无从站或无目标轴 /
**3** 有 FAIL / **4** 安全护栏拒绝 (未写任何东西) / **5** 进不去 SAFE_OP 或 OP /
**6** 过程数据未落地 (WKC 持续偏短) / **10** 收尾后 `6041h` 仍报 Operation enabled
(**电机可能仍带电**, 覆盖其它所有码)。

`--state safe-op` 只验证"补完映射后 AL `0x001E` 是否消失", 不进 OP、不写控制字。

> 无授权直接跑 `sm_pdo` 是**纯只读**的: 它会打印 `1A00h` 计数、`SM3` 长度与
> `6041h` 当前值。**期望值取决于这台设备的当前配置**:
> 若 `1A00h` = 0 项 / `SM3` 长度 = 0 (手册口径的出厂态), 就复现了那条根因;
> 若像 2026-09-15 实测那样 `1A00h` 已含 `6041h`、`SM3` = 10 字节,
> 说明配置已被改过, 那条根因在此设备上不成立。

## 多轴运动接口 motor_api (原生 SOEM)

`slide_motion` 走的是 **SDO + PP (6060h=1)**, 一次一条指令、目标值不必每周期刷新。
`motor_api` 是并列的第二个运动层, 用**过程数据**做需要每周期下发目标值的三种模式:

| 模式 | 6060h | 目标值走哪 | 用它的接口 |
|---|---|---|---|
| 位置同步 CSP | **8** | RxPDO `607Ah`, **每周期刷新** | `em_csp_move_abs/rel`, `em_csp_move_multi` |
| 速度 PV | **3** | RxPDO `60FFh`, 到位后写 0 | `em_pv_run_for` |
| 回零 HM | **6** | `6098h` 方式 + `6040h` bit4 上升沿 | `em_home` |

**本驱动器没有 CSV(6060h=9)** —— `6502h` 实测 `0xA5` = PP + PV + HM + CSP。
所以"速度模式"只能是 PV。这一条在 `ec_motor.h` 与源码注释里都写着, 免得后人再找一遍。

**为什么不能在 SDO 上做**: SOEM 的 `EC_TIMEOUTRXM` 是 **700 ms**, 而同步周期是 **ms 级**;
CSP/PV 的目标值必须每周期刷新, SDO 的往返时间根本追不上。

分层（与 `slide_motion` 的 `sm_bus` / `sm_guard` / `sm_motion` 同构）:

```text
motor_api/
├─ ec_motor.h           对外接口 (em_bus_t / em_axis_t 不透明)
├─ ec_motor_internal.h  两层之间的私有定义与写原语声明
├─ ec_motor.c           底座 —— **本目录唯一出现 ecx_SDOwrite 的文件**
├─ ec_motor_motion.c    运动层 —— 使能阶梯 / CSP 插值 / PV / 回零
└─ motor_test.c         验收程序 (S0~S8)
```

阶段: S0 开总线 / S1 选轴 / S2 实读映射与只读参数（**到此退出 0**）/
S3 补映射 + 建过程数据 + 证明偏移 / S4 进 OP / S5 使能 /
**S6 CSP 或 PV（由 `--mode` 选）** / S7 回零（方式 24）/ S8 收尾（无条件执行）。

> S6 原本分成 S6(CSP) 与 S7(PV) 两段, 现已合并成一段 —— 两者是同一件事的两种做法
> （多轴、同一个周期帧、各轴下发各自的目标值), 公共前置（失能 → 切模式 → 使能）完全
> 一样, 分开写只会把那套前置抄两遍。**旧文档里的 S7 = PV、S8 = 回零、S9 = 收尾
> 已经不成立**, 现在的 S7 是回零。

不变量: `grep -rn ecx_SDOwrite motor_api/` **只应有 `ec_motor.c` 一处**。
运动层负责"写什么、按什么顺序写、写完等哪个位", 不负责"怎么发出去"。

### 多轴怎么"同时"

`em_csp_move_multi()` 在一个循环里**一帧喂所有轴**: 逐轴按实测 `dt` 推进插值目标、
逐轴写各自的输出镜像 `6040h`/`607Ah`, 然后**才**调一次 `em_service()`。
所以"同时调用两台驱动器"具体就发生在那一次收发里 —— 不是两条独立的指令流。
各轴**各自独立**判到位（`|6064h - 终点| <= 容差` 且插值目标已到终点), 没有耦合、
没有插补、没有龙门同起同停。

### CSP 的目标位置以什么为基准

`em_csp_move_multi()` 收的是**绝对**目标位置, 接口不替调用方决定基准。
`em_csp_move_rel_multi()` 收的是**相对位移**, 基准由**接口内部**取:

> 每根轴的 `607Ah = 调用这一刻该轴的实际位置（6064h）+ delta[i]`。

关键在于"这一刻"是**同一个**决定时刻: 函数先把**所有**轴的起点读完, 再算目标,
再一次性下发。任何一根轴取不到实际位置就**整体拒绝**, 一个字节都不下发 ——
绝不像某些实现那样拿 0 当"当前位置"（那会让第一帧变成一个凭空的位置跳变）。
日志里会把每根轴的 `起点 -> 终点 (位移)` 打出来, 所以基准不是隐含的。

之所以必须做成"multi": 逐轴各调一次相对运动的话, 各轴的起点会落在**不同时刻、
不同帧**上 —— 对"两轴同时"这种用法, 那个差别正是要消除的东西。
`em_csp_move_rel()` 就是它的 n=1 薄封装。

### 偏移从哪来 (本接口最要紧的一条)

**必须先读 `1C12h` / `1C13h` 问"哪个 PDO 生效", 再按它指到的索引读映射表。**
这台设备的 `1C12h` 指的是 **`1601h`** —— 见上文「PDO 映射」。写死 `1600h` 的后果不是
报错, 而是**悄悄改错表**: 那张表里字段齐不齐都与过程数据无关, 于是"映射看着没问题"
和"控制字根本发不出去"可以同时成立, 而偏移证明还照样通过。

实测结论: 生效的 `1601h` 里 **`6040h` / `607Ah` / `60FFh` 已经齐全**
（在 +0 / +3 / +7 字节）, `1A00h` 里 `6041h` / `6064h` / `606Ch` 也齐全
（在 +0 / +2 / +6）。所以在本机上做 CSP / PV / HM **不需要改写任何 PDO 映射**
（不改映射 ≠ "不写输出镜像", 两件事 —— 见下文）。

> **旧版这里写的是「所以一个 PDO 字节都不用写」, 那个结论是错的, 也是两次真机事故的
> 直接来源。** 输出镜像的每一个字节都是主站每周期**必须**给出的: 不改映射, 但镜像里
> 属于本次运动的那些项（`6040h`/`6060h`/`607Ah`/`60FFh`/`6083h`/`6084h`）**一项都
> 不能漏**, 漏掉的那项就是每周期下发 0。正确说法是:
> **`6040h`/`607Ah`/`60FFh`/`6083h`/`6084h` 全都要逐周期驱动, `6060h` 在映射里时
> 也要; 只有 `6081h` 是有意不驱动的一项（本接口不做 PP）。**
> 判据是 `em_dump_pdo()` 里那张 7 项的处置表 —— 别凭记忆, 看表。

```
motor_test [网卡] [选项]
  --axis A,B            选轴 (总线位置, 0 起)。默认**全部**从站。
  --allow-pdo           允许补 PDO 映射 (仅 RAM) 并建过程数据。不加则跑到 S2 就退出 0。
  --allow-motion        允许使能/运动 (需 --allow-pdo)。
  --home                允许回零 (需 --allow-motion)。
  --mode csp|pv         S6 跑哪种模式, 默认 csp。
                          csp = 位置同步 (6060h=8), 相对各自起点走 --dist 再走回
                          pv  = 速度模式 (6060h=3), 跑 --pv-hold 后停并断言 bit12
  --dist PUL            CSP 位移, 默认 5000, 上限 50000 (放宽要 --force-caps)。
  --vel PUL/S           CSP 速度, 默认 5000, 上限 50000。
  --pv-vel PUL/S        PV 速度, 默认 1000, 上限 50000。
  --ramp-acc PUL/S²    6083h 轮廓加速度, 默认 500000, 上限 5000000。
                        驱动器在 PV 下靠它爬坡。**能传 0, 但 0 意味着「斜坡永远
                        起不来」** —— 现象是报"速度指令已被接受"却一步不走。
                        默认值取自驱动器 6083h 的实读值 (读不到才用这个常数)。
  --ramp-dec PUL/S²    6084h 轮廓减速度, 同上。
  --pv-hold MS          PV 保持时长, 默认 1000, 上限 3000。
  --pv-opposite         PV 时让第 2 轴反向跑 (默认两轴同向)。
  --tmo MS              单个运动超时, 默认 10000。
  --keep-mapping        跑完保留改过的映射 (默认还原)。
  --dc [周期us]         配置分布式时钟 (默认不用 DC)。
  --force-caps          放宽上面那些上限 (应当是有意的动作)。
```

参数**只支持空格分隔**（`--dist 5000`），没有 `--dist=5000` 这种写法; 传了会被当成
未知参数退出 1。数字用 `atoi` 解析, 不做尾部校验。

> 注意这里**没有** `--home-mode` / `--home-vel-*` 这类选项: 回零方式固定 24
> （原点开关 X0、正向先找), 找原点速度由 `--vel` 收紧且不超过 2000 pul/s、
> 返回速度取它的 1/4。旧版文档列过这几个选项, 实际程序里从来没有 —— 已删。

退出码: **0** 全 PASS / **1** 用法或初始化 / **2** 无可用轴 / **3** 有 FAIL /
**4** 安全护栏拒绝 / **5** 进不去 OP / **6** 过程数据未落地 / **7** 回零未达位 /
**10** 收尾未能确认失能 (**电机可能仍带电**, 覆盖其它所有码)。

> **先只跑 S0~S2**（不带任何 `--allow` 参数): 它一个字节都不写, 打印出的
> `1C12h`/`1C13h` 分配、实际生效的那张映射表、推导出的每个字段偏移, 以及
> `2201h`/`2400h`/`607Dh`/`6502h` 等只读参数 —— 这就是后面所有动作的事实依据。

### PV 怎么判"到底转没转"

`em_pv_run_multi()` 会逐轴打印 `6064h 起点 -> 终点 (走了 N pul)` 与运行期间
`606Ch` 的峰值, **位置一个计数都没变即判 FAIL**（退出码 3）。

这是 2026-09-15 那次事故补上的断言。当时 PV 全阶段 PASS、退出码 0, 而电机一步没走
—— 因为所有检查都在问「驱动器收下指令了吗」（`6041h` bit12 该清的清、该置的置、
无故障无限位, 全对), **没有一条在问「电机动了吗」**。判据必须落在这两项上:

| 观测 | 含义 |
|---|---|
| `6064h` 变没变 | **唯一的硬判据** —— 走没走, 位置说了算 |
| `606Ch` 峰值 | 辅助证据。有些驱动器会直接回报指令值, 所以它非零**不能**反推真的在转 |

CSP 一侧本来就有到位断言（`|6064h - 终点| <= 容差`), 所以没被这个坑漏过去。

### 安全边界 (与 `slide_motion` 同一套口径)

- 默认**一个字节都不写**; 写 PDO 映射要 `--allow-pdo`, 使能/运动要 `--allow-motion`,
  回零要 `--home`（它会撞限位、会找原点开关）。
- **`--allow-motion` 本身就是那句确认 —— 运行时不问 y/N。** 别在脚本里顺手加上它:
  加上就等于确认过了。这一点与 `slide_motion`（它有 `--allow-jog` + 交互确认）
  **不同**, 旧文档说 `motor_api` 也"要交互 y/N 确认"是错的。
- 上限**只能收紧, 放宽要 `--force-caps`**。按 `2400h = 50000 pul/圈` 算,
  默认 `--dist 5000` ≈ **0.1 圈**, 是刻意保守的。
- `6040h` 推送值只有 **`0x0000` / `0x0006` / `0x0007` / `0x000F`**, 回零另加 `0x001F`,
  故障复位另加 `0x0080`。**不试探厂商私有控制字。**
- **从不写 `2102h`** (EEPROM), 不改软限位 `607Dh`, 不改 `2400h`/`2408h`/`2409h`/`2201h`
  任何当量参数。默认跑完**还原** PDO 映射 (`--keep-mapping` 才留), 且只写 RAM。
- Ctrl-C 的处理器**只置一个 `volatile sig_atomic_t`**, 不在信号上下文里发 SDO;
  收尾路径**无条件执行**, 收尾后 `6041h` 仍报 Operation enabled → **退出码 10**。
- 首次回零**必须**把速度收到很低、人在物理急停旁 —— 方式 24 的物理正确性取决于现场
  接线 (`2310h` 实测 X0 = 原点、X1 = 正限位、X2 = 负限位), 不对就换 29 或 35。
- 网卡是**单进程独占** (Npcap): 与仓库的 python 链 / 其它工具**不能同时跑**。
