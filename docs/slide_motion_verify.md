# slide_motion — 滑台带动作验收验证工具

`slide_verify` 回答的是「**这台驱动器能不能被识别、能不能读**」。
`slide_motion` 回答的是下一个问题:「**它能不能按指令动作, 而且反馈和指令对得上**」。

参数错、电子齿轮错、电机相序反、编码器方向反、限位接反 —— 这些在只读验证里
全部表现为 PASS, 只有让轴真的动一次才暴露。这就是本工具存在的理由。

> **默认不动。** 不给 `--allow-motion` 时, 本工具全程只读, 一个字节都不写。
> 移动还额外需要 `--allow-jog` 与一次交互确认。

---

## 1. 阶段划分

| 阶段 | 内容 | 需要授权 | 会写吗 |
|---|---|---|---|
| **S0** | 扫描总线 + 身份判定 + 门禁 | 否 | 否 |
| **S1** | 参数矩阵与外部基线比对 | 否 | 否 |
| **S2** | OP 周期通信 + DC (**本版未实现**, 只留位置) | — | — |
| **S3** | CiA402 使能状态机 (电机通电, 不移动) | `--allow-motion` | 是 |
| **S4** | 微动 + 反馈闭环 (电机移动) | `--allow-motion --allow-jog` | 是 |
| **S5** | 收尾 / 安全停机 | 无条件执行 | 是 |

S5 在**每一条**退出路径上都会跑一次, 包括 Ctrl-C、故障、超时、掉线。
它把 `6040h` 依次推到 Disable operation → Shutdown → Disable voltage,
并把 S4 临时改过的 `6081h/6083h/6084h/6060h` 恢复成 S3 之前的快照值。

### S2 为什么本版不做

YKD2205PE 出厂默认 `1A00h` (TxPDO) 是**空的**, `1600h` 只映射了 `6040h`。
要让 PDO 通路可用, 必须用 SDO 写 `1C12h/1C13h/1600h/1A00h` —— 这改的是**驱动器
里的持久配置**, 是整套设计里最大的非必要风险(掉电是否保留取决于驱动器, 恢复逻辑
本身也可能失败)。

而 PP 模式的速度规划器本来就在驱动器内部: 只要写 `607Ah/6081h/6083h/6084h`,
再翻转 `6040h` bit4 就够跑完整动作, **不需要任何周期数据**。微动的节拍需求
(几百 ms) 远低于 SDO 往返开销带来的限制。

所以本工具走 **SDO + PRE_OP/SAFE_OP**, 零持久配置变更。OP/PDO/DC 留作后续阶段。

> **⚠ 2026-09-11 实测修正 —— 上面这条路线的主腿不存在。**
> 空 TxPDO 不只挡 OP, **也挡 SAFE_OP**: 从站拒绝 PRE_OP→SAFE_OP, AL 状态码
> `0x001E` (Invalid input configuration)。也就是说 "SDO + **SAFE_OP**" 里的
> SAFE_OP 这一半在本驱动器上拿不到, 实际只剩 PRE_OP —— 而 PRE_OP 下 CiA402
> 状态机根本不响应 `6040h`。详见 §6 的 2026-09-11 实测记录。
> 此前 `slide_verify` 的 SAFE_OP 探针把这个现象记成 WARN、并注明"默认空 TxPDO
> 是正常诱因", 把它当成无害的可选项; 就 S3/S4 而言它不是无害的, 是**堵死**的。

## 2. 用法

```bash
# 只读 (默认): 身份表 + 参数现状表
slide_motion "\Device\NPF_{GUID}"

# 只读 + 与验收基线比对
slide_motion "\Device\NPF_{GUID}" --baseline=baseline_ykd2205pe.ini

# 生成一份基线文件 (全部项都不带 '!', 由人审定后再加)
slide_motion "\Device\NPF_{GUID}" --dump-baseline=baseline_new.ini

# 预演: 跑完 S0/S1 和**动作前置检查**, 并打印将要写什么 —— 一个字节都不写
slide_motion "\Device\NPF_{GUID}" --dry-run

# 真动 (需人在设备旁, 手放急停上)
slide_motion "\Device\NPF_{GUID}" --allow-motion --allow-jog --jog=50 --vel=300
```

### 选项

| 选项 | 说明 |
|---|---|
| `--baseline=<文件>` | 与基线文件比对参数漂移 (S1) |
| `--dump-baseline=<文件>` | 导出基线后退出 (不做比对、不动作) |
| `--dry-run` | 预演 S3/S4 的写入序列 + 跑前置检查, 不写任何字节 |
| `--axis=<n>` | 只处理总线位置 n 的轴 |
| `--state=pre-op\|safe-op` | 把从站抬到哪个 AL 状态 (默认 `pre-op`) |
| `--csv=<文件>` | 把身份/参数/轨迹/微动结果导出为 CSV |
| `--allow-motion` | 允许 S3 使能 |
| `--allow-jog` | 允许 S4 微动 (必须与 `--allow-motion` 同给) |
| `--yes` | 跳过交互确认 (给自动化用) |
| `--reset-fault` | 故障态时尝试 `6040h` bit7 故障复位 |
| `--allow-foreign` | 允许总线上有非 YKD 从站时仍然动作 |
| `--force-caps` | 允许突破硬上限 (危险) |

动作参数 (`--jog` `--vel` `--accel` `--decel` `--move-tmo` `--repeats` `--tol`
`--watchdog`) 未给时取基线 `[motion]` 节的值, 再退到保守默认。

### 退出码

| 码 | 含义 |
|---|---|
| 0 | 通过: 所选阶段全部 PASS |
| 1 | 用法错误 / 初始化失败 / 基线文件打不开 |
| 2 | 空总线 |
| 3 | 存在 FAIL |
| 4 | 无 FAIL 但含 WARN |
| 5 | 总线有从站, 但一台 YKD 都没有 |
| 6 | **安全护栏拒绝, 未写任何东西** |
| 7 | **动作已开始但异常中止**(故障/丢站/超时/失速), 已执行安全停机 |
| 8 | 基线文件错误, 或 `[meta]` 身份与现场设备不匹配 |
| 9 | 使能状态机未达 Operation enabled (含 SDO abort 诊断) |
| 10 | **收尾后仍无法确认电机失能** —— 电机可能仍然带电 |

**6 与 7 的区别是有意义的**: 6 = "我检查过, 拒绝了, 什么都没动";
7 = "动过了, 出事了, 我已经停下来了"。看到 7 必须去查 6041h 与 EMCY。

**10 覆盖其它所有码**: 它表示收尾写完 `6040h=0x0000` 之后回读 `6041h` 仍然报告
Operation enabled。一个 3 分(参数漂移)和一个 10 分同时存在时报 10 —— 电机是否还
带电比任何参数比对结论都重要。看到 10 请立即按物理急停或断开驱动器电源确认。

## 3. 安全设计

### 3.1 写操作集中在一个文件

`sm_guard.c` 是**全工程唯一**出现 `ecx_SDOwrite` 的文件:

```bash
grep -rn ecx_SDOwrite slide_motion        # -> 只有 sm_guard.c 一处
```

审阅"这工具到底会往驱动器写什么"只需读这一个文件。其余文件物理上不含写操作。

#### 一个必须知道的 SOEM 行为: 加急写的 abort 会被当成成功

本仓库这份 SOEM 的 `ecx_SDOwrite` 在**加急**路径 (`psize <= 4`) 上, 把从站回的
SDO abort 帧也当成写成功: abort 响应的 mbxtype / service / index / subindex 与请求
完全相同, 于是命中 `SOEM/src/ec_coe.c` 里 "all OK" 那个分支 —— 既不进 abort 处理,
也不置 `ctx.ecaterror`, 更不压错误栈, `wkc` 还是 `> 0`。
(abort 判断只写在 `else` 分支里, 加急路径根本走不到。)

而 `6040h` 恰好是 2 字节的加急写。也就是说:**"写失能"这个动作有没有真的进驱动器,
唯一的证据是回读 `6041h`。** SOEM 是下载的第三方库, 按约定不改, 所以在
`sm_guard.c` 这一层补上回读:

- 收尾的失能序列由 `guard_force_disable()` 执行, **写完回读 `6041h` 确认 bit2 已清**,
  未确认则重试, 三次仍失败 → 退出码 10 + 醒目告警
- 参数恢复走 `guard_write_verified()`, 逐项回读比对, 只有确认一致的才计入"已恢复 N 项"
- 微动的 `607Ah` 回读失败即放弃本腿 (见 §4)

同样地, `sm_rd_raw()` 读到的宽度由驱动器自报, 但缓冲只有 4 字节 —— `sm_bytes_to_i64()`
对 1/2/3/4 字节**全部**正确解码, 包括 3 字节。掉进 `default` 分支会返回 0, 而 0 在
`60FDh` 上意味着"两个限位都没压住"、在 `606Ch` 上意味着"轴没在动" —— 用一个合法值
掩盖读失败, 比直接报错危险得多。

### 3.2 门禁 (全部在第一次写之前跑完)

1. **授权**: 无 `--allow-motion` → 只读; `--allow-jog` 必须与 `--allow-motion` 同给
2. **身份门**: 总线上有非 YKD 从站 → 拒绝动作 (除非 `--allow-foreign`)
3. **基线身份**: `[meta]` 与现场设备不符 → 退出 8
4. **dangerous 漂移**: 见下节 → 拒绝动作
5. **交互确认**: 打印授权横幅 + 行程/速度/超时, 要求输入 `yes`
6. **逐轴前置检查** (只读) —— **全部通过才动**

前置检查会在以下任一条件命中时拒绝:

- `6041h` bit3 (Fault) = 1 (除非 `--reset-fault`)
- 驱动器已处于 Operation enabled (说明有别的程序在控制它)
- `6064h` 读不到 / 跳动超过 50 脉冲 / 读数超出合理范围
- **`606Ch` 读不到** —— 读不到就无法确认轴是否正在动, 不动作
- `606Ch` 在未使能状态下不为 0 (轴正在动)
- `|当前位置| > 100000` (相对微动的原点保护, 防止 bit6 被忽略时变成不受控长距离运动)
- `60FDh` 在**本次运动方向**上的限位已触发
- `607Dh` 软限位可读时, 目标位置越界
- **`607Dh` 不可读时**行程超过 ±2000 脉冲 —— 没有任何限位兜底, 不动作

`606Ch` 读失败必须拒绝而不是"跳过这一项": 这一项问的是"轴现在是不是正在动",
答不出来就意味着可能有另一套程序 (或上一次中止的残留) 正在驱动这根轴, 此时再使能
并叠加一次微动, 等于跟未知运动抢控制权。`6041h`/`6064h` 读不到都判拒绝, 这里没有
理由例外。

`607Dh` 那一项同理: 报告里说"行程将被限制在 ±2000"而代码里没有对应约束, 是对操作者
的误导 —— 一旦有人用 `--force-caps` 放大 `--jog`, 提示与实际就分道扬镳了。所以
提示落地成真正的拒绝条件。

因为逐轴前置检查是"全过才动", **「拒绝」这个结论永远等价于「一个字节都没写」** ——
报告可以干净地说清楚。

### 3.3 dangerous 参数

`sm_spec_table[]` 里带 `dangerous` 标记的对象一旦漂移, 工具直接拒绝 S3/S4:

| 对象 | 为什么 |
|---|---|
| `2310h`~`2313h` | 限位/原点输入的功能定义, 决定 `60FDh` 每一位是什么线 |
| `2408h`/`2409h` | 电子齿轮, 决定"1 个脉冲 = 多少位移", 也决定行程断言是否成立 |
| `2204h` | 超程停车方式 |

漂移时如果继续动作, 限位保护可能是失效的, 行程换算可能是错的 —— 那样的 PASS
没有意义, 那样的 FAIL 也说不清是驱动器的问题还是参数的问题。

### 3.4 上限

CLI 只能收紧, 放宽必须显式 `--force-caps`:

| 项 | 默认 | 硬上限 |
|---|---|---|
| `--jog` 行程 | 200 脉冲 | 2000 |
| `--vel` 速度 | 500 脉冲/s | 2000 |
| `--accel` / `--decel` | 5000 脉冲/s² | 20000 |
| `--move-tmo` 单腿超时 | 3000 ms | 15000 |
| `--repeats` | 1 | 10 |
| `--watchdog` | 1000 ms | 3000 (下限 700) |
| `--tol` 容差 | 行程的 2% | 500 脉冲, 且不超过行程的 1/4 |
| 全部动作累计 | — | 15000 ms |

看门狗下限 700ms 由代码强制 (`sm_guard_check_caps`): 一次轮询最坏是 3 次 SDO 读
× 200ms = 600ms, 阈值低于它会把正常的慢轮询误判成掉线。

`--force-caps` 之上还有一道**绝对天花板** `SM_CAP_ABS_MAX = 100000`: 即使给了
`--force-caps` 也翻不过去。这不是多余的谨慎 —— 上限参数的绝对值在 int32 里取法
有陷阱: `-INT32_MIN` 溢出后仍是 `INT32_MIN` (负数), `a > hard_max` 恒为假,
`INT32_MIN` 会**原样穿过**检查, 变成一条 2³¹ 脉冲的相对运动指令, 一路直达机械
死挡。代码在 int64 里取绝对值来消除这个陷阱, 绝对天花板是第二道。

**容差也必须受上限约束。** 容差决定 A1(行程)/A6(归位) 两条断言是否还有意义:
把它放到比行程还大, 两条断言永远成立, 日志显示 PASS, 而"动得对不对"其实没被
检查过。这类"检查悄悄失效"比直接报错危险得多, 所以在 CLI 计算处和 `sm_stage_jog()`
内部各夹一次。

### 3.5 我们只清理自己接管过的轴

收尾与急停**只处理本次运行真正接管过的轴** (`sm_axis_t.engaged`, 在 S3 准备写第一个
字节时置位)。这不是优化, 是安全要求:

`--axis=0` 只检查了位置 0 那根轴, 位置 1 可能正被**另一套程序**控制。旧实现里收尾
会对总线上每一台 YKD 从站写 `0x0007/0x0006/0x0000`, 于是会把那根我们从未检查过状态
的轴一把拽停。现在的规则是: 我们只清理自己弄脏的东西。

### 3.6 只读运行不碰 AL 状态寄存器

`--dry-run` / `--dump-baseline` / 未授权运行**不再**调用 `ecx_writestate`。
它写的是从站的 AL 控制寄存器, 而且作用于总线上**每一台**从站 (含第三方从站) ——
旧实现里 `--dry-run --state=safe-op` 会把别人的从站一起推进 SAFE_OP, 与"一个字节
都不写"的承诺自相矛盾。`ecx_config_init()` 结束后从站本来就在 PRE_OP, 而只读路径
需要的正是这个状态, 所以什么都不做就是正确的。

### 3.7 看门狗是真的 dead-man 检查

掉线不会自己举手 —— 这份 SOEM 里 `slavelist[].islost` **从不被置位**, 从站静静地
不来, 只表现为 SDO 一直超时。所以判据是"距上一次成功的总线交互多久"
(`sm_guard_watchdog_expired()`), 在运动轮询里每个周期检查一次, 超时即中止。
电机带电时这是必须的。

### 3.8 Ctrl-C 的反应时间

Windows 控制处理器跑在**另一个线程**上, 而 SOEM 上下文不是线程安全的。
所以处理器**只置一个标志位** —— 不发 SDO、不 printf、不分配内存。
主线程在下一个轮询周期察觉, 由主线程执行安全停机。

最坏反应时间 ≈ `SM_SDO_TMO_MOTION` (200ms) + 一次轮询。这就是**运动期必须把 SDO
超时从 `EC_TIMEOUTRXM` (700ms) 降到 200ms** 的原因 —— 否则一次卡住的 SDO 读就能
把停机推迟到 700ms 之后。

连按两次 Ctrl-C 交给系统默认处理, 立即结束进程 (最后的逃生通道)。

> 软件急停是尽力而为。真正的保护是**物理急停**与驱动器的急停输入。

## 4. 微动是怎么判的

PP 模式的完成判据**不用** `6041h` bit10/bit12 握手 —— SDO 轮询 (5ms 节拍 + 邮箱
往返) 大概率抓不到 PP 的瞬态握手位, 靠位会误判。改用**位置静止**:

- 已动过 (`|Δpos| > 50 脉冲`) 且位置连续 150ms 不变 → 认为动作结束
- 一直没动过且超过 500ms → 失速中止 (**计时从触发那一刻起**, 不含前面几次邮箱往返,
  否则一条刚起步的健康运动可能在触发瞬间就被判失速)
- 超过本腿时间预算 (理论耗时 ×3 + 500ms, 上限 `--move-tmo`) → 超时中止
- 距上次成功总线交互超过 `--watchdog` → 按掉线中止 (见 §3.7)

触发之前还有一道前置: `607Ah` 写完**必须回读确认**才发 bit4 上升沿。回读失败即放弃
本腿 —— 在加急写路径上 (见 §3.1) 写返回成功并不能说明目标被接受, 回读是唯一的证据。

这样把「动作结束了吗」和「动得对不对」干净地分成两件事。动得对不对由断言负责:

| 断言 | 判据 | 不过时 |
|---|---|---|
| A1 行程 | `\|实测Δ - 命令Δ\| ≤ 容差` | FAIL |
| A2 方向 | `sign(实测Δ) == sign(命令Δ)` | FAIL (查电机相序) |
| A3 速度反馈 | 两腿峰值 `\|606Ch\|` 均 > 0 | FAIL (反馈链路可疑) |
| A4 限速 | 峰值 ≤ 设定速度 × 1.2 | WARN |
| A5 回程方向 | 反向腿方向正确 | FAIL |
| A6 归位 | `\|终点 - 起点\| ≤ 容差` | FAIL (丢步/反向间隙) |
| A7 单调性 | 方向违例次数 == 0 | WARN (过冲/回弹/噪声) |

容差默认取命令行程的 2% (下限 50 脉冲, 即未使能时的位置噪声水平), 可用 `--tol`
或基线 `tolerance_pct` 覆盖, 但受上限约束 (≤500 脉冲, 且 ≤ 行程的 1/4 —— 见 §3.4)。

去一趟 + 回一趟构成一个闭环: 如果 A6 过了, 说明这个轴往返之后能回到原处 ——
这是"可以放心做重复定位"的最小证据。

## 5. 基线文件

由 `--dump-baseline` 生成, 人工审定后使用。示例见
[baseline_ykd2205pe.ini](../baseline_ykd2205pe.ini)。

```ini
[meta]
vendor_id    = 0x00000994
product_code = 0x00003000

[motion]
jog_pulses    = 200
jog_velocity  = 500
jog_accel     = 5000
tolerance_pct = 5

[axis.0]
! 2310h = 1            # 行首 '!' = 必需项, 不匹配判 FAIL
  2401h = 2000         # 无 '!' = 参考项, 不匹配判 WARN
  607Dh:01 = -2000000000
```

解析规则:

- `#` 与 `;` 起注释; 空行忽略; `[节]` 切换当前节
- 键 = `IDXh:SS` (十六进制索引 + 十六进制子索引); `IDXh` 裸写 = 子索引 0
- 值 = 十进制 或 `0x` 前缀十六进制
- `[meta]` 身份不符 → 退出 8
- 基线里没写的项: 不比对, 只在 `--dry-run`/无基线时作为现状列出
- 未知节 / 未知键 / 不在 `sm_spec_table[]` 里的对象 → 打印警告并跳过, 不中断

> 想比对某个新对象, 要把它加进 `sm_baseline.c` 的 `sm_spec_table[]`,
> 光写进基线文件是不会生效的 (工具会明确告诉你这一点)。

### 代码审查发现并修复的缺陷 (2026-09-10)

### 「PRE_OP/SAFE_OP 下用 SDO 写 `6040h` 能不能打开功率级」—— 已有答案: 不能

这个问题原先留白, 2026-09-11 用独立小程序 `sm_state` 实测, 答案是不能, 但**原因
不是功率级打不开, 而是根本轮不到它**:

1. **PRE_OP 下 `6040h` 不被受理。** 写 `0x0000` (Disable voltage) 后 `6041h` 判据
   通过 (位 0-3 全 0, 未使能且无故障); 紧接着写 `0x0006` (Shutdown) 后, 161 次轮询
   `6041h` 恒为 `0x0210`, **一位都没变**。状态机在 PRE_OP 下没有启动。
2. **SAFE_OP 进不去。** 请求 SAFE_OP 后从站停在 `0x12` = `0x10`(error 位) | `0x02`
   (PRE_OP), AL 状态码 `0x001E` Invalid input configuration —— 即 §1 里那条
   "空 TxPDO 是正常诱因"的 WARN, 在 S3/S4 这条路上是致命的。
3. 两条腿都断了: 没有可达的 AL 状态能让 CiA402 状态机运转。

**要往下走, 必须先让 TxPDO 配置合法**(写 `1A00h` 与 `1C13h`, 或退一步让 SM3 有
非零长度), 也就是 §1 里被判定为"整套设计里最大的非必要风险"的那件事。换句话说,
这个根因不是可以绕开的细节, 而是**必须正面处理**的前置条件。
在解开它之前, `slide_motion --allow-motion` 的 S3 必然停在
`SM_EXIT_NO_ENABLE` (9)。

### 真机实测记录 (2026-09-10, 只读部分)

### 真机实测记录 (2026-09-11, CiA402 状态机切换)

用独立小程序 `sm_state` (只写 `6040h`, 不发运动指令) 在单台 YKD2205PE 上跑。
被测轴: 总线位置 0, 厂商 `0x0994` / 产品 `0x3000`。`6041h` 初值 = `0x0210`。

**第一轮 `--state pre-op` —— 第 0 步就失败, 且那个失败是本工具的 bug。**

断言写的是 `(sw & 0x004F) == 0x0040`, 那个 `0x0040` 是标准 CiA402 的 **bit6**
(Switch on disabled)。但 [ykd2205pe_ci402.md](ykd2205pe_ci402.md) 里本驱动器
`6041h` 的位表**只定义了 0/1/2/3/10/12, 没有 bit6**。`0x0210` 的位 0-3 全 0,
在位 0-3 的语义下就是"未使能", 第 0 步本该 PASS。

这正是 [sm.h](../slide_motion/sm.h) 文件头写明要避免的做法 ("只对文档明确列出的
位置位断言……拿一个启发式的位去判 PASS/FAIL, 会在本该通过的时候报失败")。同一处
错误还有一半: 状态名把 `0x0210` 叫 "Not ready to switch on" —— 标准里区分
"Not ready to switch on" 与 "Switch on disabled" 靠的**就是 bit6**, 该驱动器没定义,
不该替它猜, 更不该猜成听起来更像故障的那个。

已修: 断言掩码收窄为 `0x000F` (只用手册定义的位 0-3); 第 0/7 步断言改为
"位 0-3 全 0 = 未使能且无故障"; 状态名位 0-3 全 0 时统一叫 `未使能`。
> 顺带一个原理性修正: 原先第 0 步期望 `0x0040`, 即使 bit6 有定义也不成立 ——
> 写 `0x0000` 只能把驱动器拉进 Switch on disabled, 而
> "Not ready to switch on → Switch on disabled" 是驱动器**内部初始化完成的自动
> 迁移**, 控制字触发不了它。所以这一步的期望值只能是"未使能且无故障"。

**第二轮 `--state safe-op` —— 拿到真结论。**

```
目标轴: 位置 0, AL 状态 0x12 (请求 SAFE_OP)
  0. 归位 Disable voltage  写 6040h=0x0000 ... [PASS] 0x0210 (未使能)
  1. Shutdown              写 6040h=0x0006 ... [FAIL] 断言未成立
       期望 6041h & 0x000F == 0x0001, 实测 0x0210 (未使能) (161 次读数)
       EtherCAT AL 状态=0x12, AL 状态码=0x001E Invalid input configuration
```

要点:

- 写 `0x0006` 之后 **161 次轮询 `6041h` 恒为 `0x0210`, 一位未变** —— PRE_OP 下
  CiA402 状态机不响应 `6040h`, 与第一轮一致。
- AL 状态 `0x12` = `0x10` (EC_STATE_ERROR) | `0x02` (PRE_OP): 从站**拒绝**进入
  SAFE_OP 并置错误位, AL 状态码 `0x001E` Invalid input configuration。
  这就是 §1 里那条"空 TxPDO 是正常诱因"的 WARN 的原始形态。
- 全程**没有故障**: 位 3 始终 0, AL 状态码在进 SAFE_OP 之前是 `0x0000 No error`。
  驱动器是好的, 是配置不具备。

**结论**: 详细论证见上文《「PRE_OP/SAFE_OP 下用 SDO 写 `6040h` 能不能打开功率级」
—— 已有答案: 不能》。一句话 —— 空 TxPDO 既挡 OP 也挡 SAFE_OP, 而 PRE_OP 下状态机
不跑; 本工具"零持久配置变更"的路线在当前出厂配置下到不了 S3。

**遗留的代码问题** (未修, 记在这里): `sm_state` 请求 SAFE_OP 后只打印了从站报回的
`0x12`, 没有把 `0x10` 错误位与 AL 状态码升起为显式失败 —— 进 SAFE_OP 失败时应当
像 `slide_verify` 的 SAFE_OP 探针那样直说, 而不是把它留在一行状态打印里。
