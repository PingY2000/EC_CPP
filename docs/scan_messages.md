# scan 提示语背后的成因与排查表(2026-09-23)

本文是**界面提示语的另一半**。界面上只留三样东西:

1. **现在是什么状况**(客观陈述句;限位开关一律说「触发 / 未触发」);
2. **一句出路**,写成「请……」(真的需要人动手时才写);
3. 数字与寄存器读数原样(`6041h bit3` / `60FDh` / `603Fh = 0xFF02`)。

**成因、几种可能、先查哪一个、为什么这么设计** 全部搬到本文。理由与规范见
[`scan_sweep.md` §26](scan_sweep.md)。改提示语时先在这里找到那一节,再决定界面上留哪一句 ——
不许在界面上再长出第二段解释。

对应关系是**一对多**:界面上一句「正限位与负限位同时触发」在下面可能有三条成因,操作员要按
现场情况自己往下走。反过来,**本文里任何一句都不许原样抄回界面**。

---

## 1. 限位判据:三条规则,同一时刻只有一条生效

判据本体在 `hmi/ecatworker.h` 的 `limit_hit_rule()`,**只此一处**;选哪条规则在 `limit_rule_for()`。

| 规则 | 何时生效 | 判据 | 60FDh 读不到时 |
|---|---|---|---|
| `LIMIT_RULE_BIT11` | 出厂默认 | `6041h` bit11 单独判定 | 照 bit11 判 |
| `LIMIT_RULE_REFINED` | `kRefineLimitWithDigIn = 1`(未启用) | bit11 **且** 60FDh 说正/负限位触发(原点不算) | 退回 bit11 单独判定 |
| `LIMIT_RULE_INVERT` | 「上位机侧取反」勾上 | **只看**反相之后的两个限位开关,bit11 不参与 | **一律判成成立** → 中止 |

三个键的事实:

- `6041h` bit11 = 「硬件限位信号有效时置 1」(ykd 手册 V2.4 的 6041h 表)。它是**电平**不是闩锁,
  与 60FDh 的 bit0/bit1 同源。所以界面措辞一律是「有效 / 触发」,**不说「撞上」**。
- `60FDh` bit2/1/0 = 原点 / 正限位 / 负限位开关**本身**的状态(`2310h` X0 / `2311h` X1 /
  `2312h` X2)。**原点那一位不参与任何中止判定** —— 扫描区域本来就可能压在一个开关上。
- 两者**可能不一致**(开关触发而驱动器没置 bit11,或者反过来)。不一致时以 bit11 为准
  (反转开着时反过来:以 60FDh 为准)。

`LIMIT_RULE_INVERT` 为什么把「读不到」判成成立:另外两条规则都有 bit11 可退,只有它没有 ——
反相之后那两个开关是**唯一**判据,读不到就等于没有保护,**宁可多报**。

## 2. 60FDh 读不到

**界面原话**:「60FDh 读不到, 三个开关的状态无从得知」;取反开着时多一句「无可用限位判据」。

**成因**:`60FDh` 不在生效的 `1A00h` TxPDO 映射里。本机出厂映射就是这样 —— 本程序默认**只绑不补**,
不动驱动器的映射。

**出路**:

1. 勾「让 60FDh 进 TxPDO」,再重新「连接」(这是**连接期**参数,当次连接改不了)。
2. 或者接受现状:三个开关状态看不见,限位保护仍由 `6041h` bit11 承担(即 `LIMIT_RULE_BIT11`)。
   只有「上位机侧取反」开着时这条退路不存在 —— 那时扫描无法启动,必须先做第 1 条。

**连带**:回零的 17/18 方式靠 60FDh 分 a) / b) 分支(见 §4),读不到时**拒绝找限位**
(「拒绝找限位」是界面上的原话,不要改)。

---

## 3. 正限位与负限位同时触发

物理上不成立 —— 两个开关同时压住意味着滑台同时贴在两头上。界面上只说这一句,成因有三种:

### 3.1 `2300h` 输入有效电平逻辑配反(现场见过的那一台)

X0~X3 接的是 NPN 传感器(高电平 = **未**触发),而 `2300h` 按常开配 → 驱动器把「没触发」
读成「触发」,两路输入**常年**读成触发,`6041h` bit11 恒为 1。定位与限位判据一起错,
扫描可能开不了。

**查**:`2300h` 的低三位;勾上「写驱动器 2300h」会在连接时把它写成 NPN 该有的 `0x0007`
(只有勾了才写,写入前会先只读探一遍原值)。控制台里每次都打出现读数、字节数与每一位的
常开/常闭。

**软件侧出路**:「上位机侧取反」。它**只作用于本程序**(不动驱动器的 `2300h`,也不动 bit11),
反相之后两个开关的含义才对。**它与「写驱动器 2300h」不能同时勾** —— 见 §3.4。

### 3.2 传感器供电与接线

- 传感器没供电 / 供电被拉到 0V → 输入常读成高电平;
- 两根限位的线接反或接串 → 一路动两路都动;
- 传感器类型与接线方式不匹配(NPN 接了 PNP 的公共端之类)。

**查**:先量两路输入在滑台居中时的电平;再单独压住一路,看只有它变。

### 3.3 上位机侧取反开着时的「同时触发」

反相之后的值仍然同时为真 → 这一条**与 2300h 无关**(极性错只会把两边一起反相,反相完就该
松开)。所以此时界面措辞里**不再提 2300h**,而是指向供电与接线。

### 3.4 双反相(两个勾同时勾上)

「写驱动器 2300h」与「上位机侧取反」都勾着 = 把同一件事反了两遍。判据此时是
`LIMIT_RULE_INVERT`,而反相之后那两位空载时都是 1 → **判据恒成立** → 扫描永远开不了。

正解只有一个:把「上位机侧取反」关掉。界面上的警告原话是
`双反相: … 限位判据恒成立, 扫描无法启动。请关闭「上位机侧取反」。`

## 4. 单侧限位触发 / 仅原点触发

**单侧触发**:滑台确实停在该侧限位上,或者 `607Dh:01/:02` 的软限位比机械限位更早介入。

界面出路是「请手动把滑台移离该限位」,再查 `607Dh:01/:02`。**不要**把限位判据改掉来绕过它 ——
那是保护。

**仅原点触发**:原点开关属**位置信息**,不是故障,不中止扫描,也不影响起扫判定。它会出现在
「轴信号」栏的 60FDh 那一组灯里(绿亮 = 触发)。

---

## 5. 找限位(方式 17 / 18)与 a) / b) 分支

`6098h` = 18(找正限位)/ 17(找负限位)。这两条与 24 / 29(找原点)的**基准不同**:
24/29 找的是原点开关 X0,17/18 找的是**那一侧的限位开关**。手册 V2.4 p46~p48 给 17/18
各写了两条分支:

- **a) 分支**(发起时目标开关**未触发**):先朝它**高速**去寻找,碰到后减速停止,再**反向低速**
  退开;
- **b) 分支**(发起时目标开关**已触发**):直接朝**反方向低速**退开。

两条分支的终点都是开关的**释放点**(刚退开一点的那个位置),坐标 0 就落在那里。所以:

- b) 的**首段方向与 a) 相反** —— 看到它先往反方向走不是点错了,界面发起前那句预告就是为
  这件事写的(两句话里都必须写明方向与快慢);
- 发起找限位前**先失能**(`doHome()` 的第一件事是 `em_disable()`,会撤掉保持力矩);
- 「触发限位」在找限位这一趟里是**预期结果**,不是故障。

**拒绝找限位**的两种情形(界面原话都是「拒绝找限位」):

| 情形 | 成因 | 出路 |
|---|---|---|
| 60FDh 读不到 | 分不出这一趟走 a) 还是 b) | 勾「让 60FDh 进 TxPDO」并重新连接 |
| 目标侧与另一侧**同时**报有效 | 这一对读数至少有一个不是真的(见 §3) | 查 `2300h` 与 X0~X3 接线 |

## 6. 回零失败(界面只说「失败, 请查看控制台……」)

界面那一格混着**至少五种**原因,所以它不能替人猜方向 —— 具体是哪一个在控制台那几行里
(`6061h` / `bit12` / `bit3` / `bit13`)。

| 控制台里看到 | 成因 | 处置 |
|---|---|---|
| `6061h` 不是 6(HM) | 驱动器没接受回零模式 —— 最常见的一个 | 查 `6098h` 写入是否返回成功、驱动器是否在 OP |
| rc 非 0 且 `bit12` 一直是 0 | 等 `6041h` bit12(Homing attained)超时 | 速度 × 超时的可达距离够不够;开关是否在可达范围内(超时不是停止条件,触发硬件限位才停) |
| `bit3` 立起 | 期间报了驱动器故障 | 查 `603Fh`(§7) |
| `bit13` 立起 | 回零出错位 | 驱动器侧回零配置(斜率 / 参考点开关掩码 `6098h` 一族) |
| 方向不对 | 「正/反」是**电机轴**的正反向,与画布 +X/+Y 是否同向只有现场试一次才知道 | 换另一个方向的方式号;撞着开关还硬回才是真会伤机器的做法 |

**被「停止」中止不是失败** —— 那是人让它停的,界面措辞里有这一条(自检钉着)。

**「回零校准」一次点名两根轴时多出来的两句**(2026-09-24,见 `scan_sweep.md` §33.9):

| 界面原话(要点) | 成因 |
|---|---|
| 「**轴X 轴Y** 回零未发起, 驱动器未写入。」+ 拒因 | 起手预检没过。总线级三道(未连上 / 一份完整 `6064h` 都没取到 / 还有轴在走)不点任何一根的名;逐轴两道(**这一根没收到过完整帧** / **`6041h bit3 = Fault`**)点名那一根。**一根不合格就两根都不动**,所以这句话出现时台上什么都没发生 —— 它描述的不是"失败",是"压根没开始" |
| 「回零结果: 轴X 到位, 轴Y 未到位。**请查 轴Y**。」 | 批级总结, 只报**是哪一根**。这一根**具体**为什么未到位, 在它自己那一句里(`6061h` / `bit12` / `bit3` / `bit13`, 见上表) |
| 「未到位」但**没被点名** | 它是**被对侧带停**的, 不是元凶。与单轴的「被「停止」中止」是同一类: 结局为真, 但**不是它的错** |

最后一行是这张表最要紧的一条。**元凶判定是两趟**(`home_batch_blame`):

1. 先找**第一个 `rc < 0`** 的轴 —— 故障 / 收尾出错位 / 超时 / 帧断 / 起手失败。
   **被「停止」打断的不算**在这里, 那是操作员自己按的。
2. 找不到才走兜底, 而兜底**只在真有「被带停」的轴时才走**, 并且**避开**被带停的那一根。

于是点出来的要么是**自己出事的**, 要么是**把别人带停的**, **绝不会是被带停的那一根**。
点错一根的后果是把一根好轴支去查 —— §33.8 记着这个错真的写出来过(靠推理发现, 不是靠断言)。

**收尾结局**(`home_end_state()` / `home_end_text()`,判据是收尾**那一刻的实测状态**,不是三个
返回码的排列组合):

| 结局 | 含义 | 界面原话要点 |
|---|---|---|
| `HOLDING` | 已使能 + 已是 CSP,停在落点带保持力矩 | 「带保持力矩」 |
| `STRANDED` | 收尾没确认到「已使能 + CSP」→ **电机可能仍带电**,而驱动器不按 CSP 解释 `607Ah` | 「可能仍带电」,并要求断开动力电源 |
| `FAULTED` | 该轴报 `6041h` bit3,停在未使能 | 指到「故障复位」 |
| `NEVER_STARTED` | 前置判据没过,压根没发起 | 闸拦下时现场有故障也不算「这次回零把它搞坏了」 |

## 7. `603Fh` 故障码表

`6041h` bit3 只说「有故障」,**说不了是哪一个** —— 那件事只有 `603Fh` 说。两个来源
(`err_code_from()` **唯一一处**决定挑哪个):映射里有就读过程数据那一个(与 bit3 同帧到达),
不在映射里就走 SDO 回退,而回退**只在 bit3 立起时走**。

| 码 | 含义 | 处置 | ALM 灯红闪次数 |
|---|---|---|---|
| `0x0000` | 无错误 | 码是好的,只是故障位还没清 → 「故障复位」 | 不闪 |
| `0xFF01` | 过流 | 机械卡死 / 堵转;动力线 U V W | 1 |
| `0xFF02` | 过压 | 供电电压;减速设置 | 2 |
| `0xFF03` | 欠压 | 供电与接触器 | 3 |
| `0xFF04` | 动力线报警 | 动力线接线;电机相间 / 对地 | — |
| `0xFF06` | 通讯报警 | 通讯线、干扰源、站号配置 | 6 |
| `0xFF08` | 传感器告警 | 编码器接线与信号 | 8 |

**表外码照实报十六进制**(`0xFF02 (手册之外)`),不猜成「未知故障」。

**两个「不知道」必须分开说**:「还没读到 (正在读)」= 再等一帧就有;「读不到 (SDO 没应答)」=
这一趟读不到了。

**ALM 灯可对账**:面板上数出来的红闪次数就是上表那几个数字。数出来与读到的码对得上,
说明这条 SDO 读的是同一件事;对不上就先别信读到的码。

---

## 8. 通讯:`WKC` 不足是谁的错

界面只写「过程数据帧连续 %1 帧不足 (工作计数器 %2/%3)」—— 这是**上位机自己看到的**(B 家族),
与驱动器自报的 `0xFF06`(A 家族)是两件事,措辞刻意不共用。

成因(按现场概率):

1. 网线或接头拔了、接触不良、拖链里被磨断;
2. 驱动器侧掉电或掉出 OP(`AL` 状态码见 §9);
3. 某一个从站没进 OP(留在 PRE-OP 的从站不参与过程数据交换,会让**整帧**的 WKC 持续偏短)
   —— 所以 `em_setup` 选的是**总线上全部从站**,不是「前两台」;
4. 干扰(变频器 / 伺服动力线并行走线)。

界面只报「过程数据不完整, 扫描未启动 / 扫描自动中止」,**不写「查网线」** —— 上面四条里
只有第 1 条是网线。

单帧抖动不值得报警:要**连续 10 帧**(30Hz 下约 1/3 秒)才认。

**最长未发帧时间**(`max_gap_ms`)是另一个方向的证词:本程序自己最长多久没发出一帧。
它与 WKC 不足同时出现 = 问题在这一侧的调度或阻塞命令上,不在线缆上。

### 8.1 停顿已过去、从站还没回来(2026-09-23)

上一条只说了一半。现场实机那条是真的**停顿**:空闲无人操作时,本程序**最长 1657 ms 一帧都没
发出去**(超 50 ms 共 12 次)。后果不是"漏了几帧",而是**从站不回来了**:

上位机停顿 1.6 s → 两台驱动器的 SM 看门狗动作(`AL` `0x14` = SAFE-OP + 错误位,
状态码 `0x001B`,见 §9)→ 从站停止过程数据交换 → `WKC` 恒为 2/6 → 各轴 `mirror_ok` 降 0
**且再也升不回来**(它只在收到完整帧时置位)→ 复位/使能全部被有效地拒,
**唯一的回程是「断开 → 重连」**。

所以有几句话是**分开的两件事**,不许互相冒充:

| 局面 | 该说的 | 不许说的 |
|---|---|---|
| 帧不足、`6041h` 是陈旧值 | 「6041h 是**陈旧值**,判不了有没有故障,**一个字节都没写**」,处置指向通讯 | 「无轴报故障(6041h bit3 均为 0)」—— 那是把"判不了"说成"没有",与同一块屏幕上刚说过的"陈旧值"直接打脸 |
| 帧不足、点「使能」失败 | 「这次失败**与驱动器的故障位、限位无关**」 | 「请确认 6041h 故障位与限位状态」—— 那句话的前提是"我看得见驱动器状态" |
| 本机停顿造成的静默 | 「是**这台机器自己**的停顿,不是从站的问题」,处置指向电源计划 / 网卡节能 | 去动从站的 `AL` 寄存器 |
| 自动恢复**动手前**那句 | 「本机已连续 N 帧按时发出,而过程数据帧仍连续 M 帧不足」—— 两件都真查过,带数字 | 「从站仍不在 OP」—— 判据里**没有一条读 `AL`**,而那句话说出口之后下一句就可能打脸 |

**归因必须分两份**:`max_gap_ms`(全程最长,含**本程序自己的命令**造成的静默 —— 复位/使能/
回零期间 SOEM 的 SDO 事务一帧都不发)与 `max_gap_self_ms`(其中自家那一份)。自动重请求 OP 的
触发**只看净的外部停顿**:不分开的话,我们自己一次使能造成的 1 秒静默会被读成"这台 PC 在卡"。

自动重请求 OP 的判据(`ecatcmd::recover_verdict`)量的是**上位机**够不够稳 ——
即连续多少帧**按时**发出去(`gap_ok_run`),**不是** WKC。用 WKC 会永远不动手:从站一旦掉出
OP,WKC 就恒为 2/6,那个数永远涨不上去。三种"不动手"的局面(没答话 / 停在 INIT / 混合局面)
一个 `AL` 字节都不写,只喊人;`RECOVER_MASTER`(眼下这一帧就迟到了)压过
`RECOVER_GIVEUP`(本会话试满了)—— 顺序是内容,**先说根因**。

**动手要两个条件同时成立,各管一头**(2026-09-23 第一次实跑补上第二条):
`recover_verdict` 问"本机够不够稳、还有没有机会"(上位机侧)与 `recover_bus_broken`
问"总线是不是真的需要救"(总线侧)。少了后者,一条**健康**的总线在连上约 2 秒后就会被点着 ——
第一趟触发时它自己紧接着报「所有从站的 AL 都在 OP」。`RECOVER_MASTER` 不受总线那道闸管。

**触发前那句话只许说真的查过的事**。曾经写的是「本机已经稳了一阵子而**从站仍不在 OP**」,
而判据里一条读 `AL` 的都没有 —— 同一段日志里它下一句就是「所有从站的 AL 都在 OP」。
现在的原话是「本机已连续 %1 帧按时发出,而过程数据帧仍连续 %2 帧不足」:两件都真的查过,且带数字。

**`AL` 状态字 bit4 是闩锁,清它要单独一步**:写 `当前那一级 | ACK`,然后每圈照常发过程数据
等它自己消失,再往上爬。把它与目标级(OP)一起写、或者清错期间断帧,都会让从站把这次
看门狗告警再分一次 —— 症状是"重请求了但没上去",而那看起来像"这个功能没用"。

### 8.2 节拍一直慢着(2026-09-24)

§8.1 那把尺(`max_gap_ms`)量的是**最长一次停了多久**,而且是离群点判据(> 50 ms)。它有个
盲区,这次在真总线上查出来了:**节拍均匀地慢下来,它看不出来。**

现场症状是「连上、放着不动,过一会儿断连」。实机复现(真总线、进 OP、只喂帧不发命令,
一趟 30 分钟)量到的正是这个盲区:`max_gap_ms` 那一整趟记到的是一个 **79 ms** 的离群点,
而**同一趟里帧周期是 15.8 ms(全程)** —— 它报出来的那个数与"节拍"根本不是一回事:一圈
均匀地慢下来时,它要么什么都不记(没有超过 50 ms 的那一次),要么只记下偶然的那一两次,
**屏幕上没有任何一个字解释"每一帧都迟到了"**。

病态那趟不是漏了几帧 —— 是**每一帧都迟到**:上位机的节拍 `em_sleep_ms(2)` 实际睡掉一个
系统 tick(15.6 ms),一圈慢 8 倍(正常 2.5 ms)。驱动器每 2 ms 就该收到一帧,一直这样喂,
它的 `SM` 看门狗迟早动作,接着就是 §8.1 那条链(掉出 OP → `WKC` 恒 2/6 → `mirror_ok` 降 0
且升不回来 → 只能重连)。

**节拍慢的根因是 `Sleep()` 的粒度**:它由本进程有没有"1 ms 定时器精度请求"决定(Windows 10 2004 起
该请求是 per-process 的),而 Windows 会把没人操作用的后台进程的精度请求丢掉。处置在
[`scan_sweep.md` §34](scan_sweep.md) —— 一句话:节拍换成高精度可等待定时器,并在工作线程
起手拒绝省电节流。

**另外加一把尺:平均帧周期。** `BusTelem::period_avg_ms` = 最近 64 帧的平均;
`ecatcmd::cadence_slow` 判它超过 3 倍圈期。

| 界面 | 原话 |
|---|---|
| 状态栏(`scan` 与 `hmi` 同一句) | 「WKC 6 / 期望 6 · 帧周期平均 16 ms (上限 6 ms)」 |
| 通讯横幅(帧不足那一刻) | 多一句「本程序帧周期平均 16 ms (上限 6 ms)。」 |

**它与 `max_gap_ms` 是两个数,不许互相顶替**:那个是"最长一次"(离群点),这个是"整条节拍
多快"。同一趟 30 分钟里前者说 79、后者说 15.8,谁也替不了谁。

**上限取 3 倍圈期而不是写死一个数**,实测把它夹在中间:正常 2.5 ms 之下、病态 15.9 ms 之上,
离两边都远(2.4 倍 / 2.6 倍)。

**它不并进 `comm_bad`**:那条线会去点自动重请求 `OP`,也就是往从站的 `AL` 寄存器里写字节;
而"本机节拍慢"还不到该动寄存器的程度,它该做的是让人看见。所以状态栏那一句**不受**"出过事
才常驻"那道闸管 —— 等 `comm_bad` 立起来再说,就已经断连了。没量到(< 1 窗)与正常一样,
一个字都不出。

## 9. `AL` 状态码(从站侧)

表照 SOEM 的 `ec_ALstatuscodelist` 手抄(自检不链 SOEM,所以判据那边自带一份)。
只抄这台机器真可能撞上的那几条,认不出的回落到十六进制。

真正常见的:

| 码 | 含义 | 备注 |
|---|---|---|
| `0x0011` | 被要求的状态迁移不合法 | 一般是主从状态不同步 |
| `0x0017` | 同步管理器配置不合法 | 映射 / SM 设置 |
| `0x001B` | 同步管理器看门狗(主站喂帧超时) | **与 `603Fh = 0xFF06` 说的是同一件事**,一个在从站侧报、一个在驱动器侧报 |
| `0x0020` | 从站需要冷启动 | 断电重启 |
| `0x0034` | DC 同步超时 | 本程序**不上 DC**(SM 同步 / 自由运行) |

**`1C32h:01` 报 2(DC 同步)而本程序不发 SYNC0** 是一条单独的坑:那类报警与上位机发不发帧
无关,需要另配驱动器。连接时控制台会打出 `1C32h:01/:02` 与 `2217h` 的读数(都在 `consoleNote`
里,不在界面上)。

## 10. 软件侧的确定性错误(与控制台 / CSV 有关)

这几条不是硬件问题,成因单一,但界面也只用一句话:

| 界面原话 | 成因 |
|---|---|
| 「未到位: 下发目标 … 始终未进入容差」 | 机械卡住 / 被限位挡住 / 目标被量程夹掉。第三种最隐蔽:超出量程的目标会被**静默夹掉**,不报错 |
| 「区域超出量程」 | 网格最远点超出当前软量程。参数刚改过时量程要等工作线程转一圈才跟上,此时启扫会撞上这一条 |
| 「该 CSV 采于另一次零点」 | 回零与「设为区域中心」都会**搬动**零点(重新连接不会)。同一个坐标可能已指向另一个物理位置,接着扫会把两份数据拼在同一张图上 |
| 「区域 / 分辨率 / 每 mm 脉冲数已改动」 | 单点重测是把一行**追加**到那个 CSV 里;几何变了以后 `(ix,iy)` 已不是文件里那一点 |
| 「点数 %lld 超出上限」 | 上限是一道资源闸(见 `scanplan.cpp` 的点数上限一节)。常见成因是分辨率少打一位 |
| 「收尾时未能确认所有轴已失能」(模态,`hmi` 与 `scan` 同一句) | 收尾过程中总线已经掉了:驱动器还带着力矩,而主站已经没有通道去撤它。**软件到这一步没有补救手段**,所以那一句只留「请立即断开动力电源」—— 这是全程序唯一一条"别信软件"的提示 |

## 11. 改界面提示语时的检查清单

1. 这一句说的是**状况**还是**成因**?成因 → 写进本文,界面上不留。
2. 有没有替操作员决定下一步?有 → 删掉,除非真的只有一条出路,那就写成一句「请……」。
3. 限位开关的词是不是「触发 / 未触发」?
4. 数字与寄存器是不是原样(`6041h bit3` / `0xFF02`)?
5. 长度还在 [`scan_sweep.md` §26](scan_sweep.md) 那张表内吗?
6. 改到 `hmi/ecatworker.h` 的 `ecatcmd::*` 函数时,`scan/selftest.cpp` 里钉着那些词 ——
   断言允许在**同一层**上机械调整(比如「都没压着」→「都没触发」),但**钉住的判据本身**
   (必须点名的码 / 必须出现的出路 / 不能出现的猜测)一条都不许删。
