# scan 提示语背后的成因与排查表(2026-09-23)

本文是**界面提示语的另一半**。界面上只留三样东西:

1. **现在是什么状况**(客观陈述句;限位开关一律说「触发 / 未触发」);
2. **一句出路**,写成「请……」(真的需要人动手时才写);
3. 数字与寄存器读数原样(`6041h bit3` / `60FDh` / `603Fh = 0xFF02`)。

**成因、几种可能、先查哪一个、为什么这么设计** 全部搬到本文。理由与规范见
[`scan_sweep.md` §26](scan_sweep.md)。改提示语时先在这里找到那一节,再决定界面上留哪一句 ——
不许在界面上再长出第二段解释。

对应关系是**一对多**:界面上一句「正限位与负限位同时触发」在下面可能有三条成因,操作员要按
现场情况自己往下走。反过来,**本文里任何一句都不许原样抄回界面**。

---

## 1. 限位判据:三条规则,同一时刻只有一条生效

判据本体在 `hmi/ecatworker.h` 的 `limit_hit_rule()`,**只此一处**;选哪条规则在 `limit_rule_for()`。

| 规则 | 何时生效 | 判据 | 60FDh 读不到时 |
|---|---|---|---|
| `LIMIT_RULE_BIT11` | 出厂默认 | `6041h` bit11 单独判定 | 照 bit11 判 |
| `LIMIT_RULE_REFINED` | `kRefineLimitWithDigIn = 1`(未启用) | bit11 **且** 60FDh 说正/负限位触发(原点不算) | 退回 bit11 单独判定 |
| `LIMIT_RULE_INVERT` | 「上位机侧取反」勾上 | **只看**反相之后的两个限位开关,bit11 不参与 | **一律判成成立** → 中止 |

三个键的事实:

- `6041h` bit11 = 「硬件限位信号有效时置 1」(ykd 手册 V2.4 的 6041h 表)。它是**电平**不是闩锁,
  与 60FDh 的 bit0/bit1 同源。所以界面措辞一律是「有效 / 触发」,**不说「撞上」**。
- `60FDh` bit2/1/0 = 原点 / 正限位 / 负限位开关**本身**的状态(`2310h` X0 / `2311h` X1 /
  `2312h` X2)。**原点那一位不参与任何中止判定** —— 扫描区域本来就可能压在一个开关上。
- 两者**可能不一致**(开关触发而驱动器没置 bit11,或者反过来)。不一致时以 bit11 为准
  (反转开着时反过来:以 60FDh 为准)。

`LIMIT_RULE_INVERT` 为什么把「读不到」判成成立:另外两条规则都有 bit11 可退,只有它没有 ——
反相之后那两个开关是**唯一**判据,读不到就等于没有保护,**宁可多报**。

## 2. 60FDh 读不到

**界面原话**:「60FDh 读不到, 三个开关的状态无从得知」;取反开着时多一句「无可用限位判据」。

**成因**:`60FDh` 不在生效的 `1A00h` TxPDO 映射里。本机出厂映射就是这样 —— 本程序默认**只绑不补**,
不动驱动器的映射。

**出路**:

1. 勾「让 60FDh 进 TxPDO」,再重新「连接」(这是**连接期**参数,当次连接改不了)。
2. 或者接受现状:三个开关状态看不见,限位保护仍由 `6041h` bit11 承担(即 `LIMIT_RULE_BIT11`)。
   只有「上位机侧取反」开着时这条退路不存在 —— 那时扫描无法启动,必须先做第 1 条。

**连带**:回零的 17/18 方式靠 60FDh 分 a) / b) 分支(见 §4),读不到时**拒绝找限位**
(「拒绝找限位」是界面上的原话,不要改)。

## 3. 正限位与负限位同时触发

物理上不成立 —— 两个开关同时压住意味着滑台同时贴在两头上。界面上只说这一句,成因有三种:

### 3.1 `2300h` 输入有效电平逻辑配反(现场见过的那一台)

X0~X3 接的是 NPN 传感器(高电平 = **未**触发),而 `2300h` 按常开配 → 驱动器把「没触发」
读成「触发」,两路输入**常年**读成触发,`6041h` bit11 恒为 1。定位与限位判据一起错,
扫描可能开不了。

**查**:`2300h` 的低三位;勾上「写驱动器 2300h」会在连接时把它写成 NPN 该有的 `0x0007`
(只有勾了才写,写入前会先只读探一遍原值)。控制台里每次都打出现读数、字节数与每一位的
常开/常闭。

**软件侧出路**:「上位机侧取反」。它**只作用于本程序**(不动驱动器的 `2300h`,也不动 bit11),
反相之后两个开关的含义才对。**它与「写驱动器 2300h」不能同时勾** —— 见 §3.4。

### 3.2 传感器供电与接线

- 传感器没供电 / 供电被拉到 0V → 输入常读成高电平;
- 两根限位的线接反或接串 → 一路动两路都动;
- 传感器类型与接线方式不匹配(NPN 接了 PNP 的公共端之类)。

**查**:先量两路输入在滑台居中时的电平;再单独压住一路,看只有它变。

### 3.3 上位机侧取反开着时的「同时触发」

反相之后的值仍然同时为真 → 这一条**与 2300h 无关**(极性错只会把两边一起反相,反相完就该
松开)。所以此时界面措辞里**不再提 2300h**,而是指向供电与接线。

### 3.4 双反相(两个勾同时勾上)

「写驱动器 2300h」与「上位机侧取反」都勾着 = 把同一件事反了两遍。判据此时是
`LIMIT_RULE_INVERT`,而反相之后那两位空载时都是 1 → **判据恒成立** → 扫描永远开不了。

正解只有一个:把「上位机侧取反」关掉。界面上的警告原话是
`双反相: … 限位判据恒成立, 扫描无法启动。请关闭「上位机侧取反」。`

## 4. 单侧限位触发 / 仅原点触发

**单侧触发**:滑台确实停在该侧限位上,或者 `607Dh:01/:02` 的软限位比机械限位更早介入。

界面出路是「请手动把滑台移离该限位」,再查 `607Dh:01/:02`。**不要**把限位判据改掉来绕过它 ——
那是保护。

**仅原点触发**:原点开关属**位置信息**,不是故障,不中止扫描,也不影响起扫判定。它会出现在
「轴信号」栏的 60FDh 那一组灯里(绿亮 = 触发)。

---

## 5. 找限位(方式 17 / 18)与 a) / b) 分支

`6098h` = 18(找正限位)/ 17(找负限位)。这两条与 24 / 29(找原点)的**基准不同**:
24/29 找的是原点开关 X0,17/18 找的是**那一侧的限位开关**。手册 V2.4 p46~p48 给 17/18
各写了两条分支:

- **a) 分支**(发起时目标开关**未触发**):先朝它**高速**去寻找,碰到后减速停止,再**反向低速**
  退开;
- **b) 分支**(发起时目标开关**已触发**):直接朝**反方向低速**退开。

两条分支的终点都是开关的**释放点**(刚退开一点的那个位置),坐标 0 就落在那里。所以:

- b) 的**首段方向与 a) 相反** —— 看到它先往反方向走不是点错了,界面发起前那句预告就是为
  这件事写的(两句话里都必须写明方向与快慢);
- 发起找限位前**先失能**(`doHome()` 的第一件事是 `em_disable()`,会撤掉保持力矩);
- 「触发限位」在找限位这一趟里是**预期结果**,不是故障。

**拒绝找限位**的两种情形(界面原话都是「拒绝找限位」):

| 情形 | 成因 | 出路 |
|---|---|---|
| 60FDh 读不到 | 分不出这一趟走 a) 还是 b) | 勾「让 60FDh 进 TxPDO」并重新连接 |
| 目标侧与另一侧**同时**报有效 | 这一对读数至少有一个不是真的(见 §3) | 查 `2300h` 与 X0~X3 接线 |

## 6. 回零失败(界面只说「失败, 请查看控制台……」)

界面那一格混着**至少五种**原因,所以它不能替人猜方向 —— 具体是哪一个在控制台那几行里
(`6061h` / `bit12` / `bit3` / `bit13`)。

| 控制台里看到 | 成因 | 处置 |
|---|---|---|
| `6061h` 不是 6(HM) | 驱动器没接受回零模式 —— 最常见的一个 | 查 `6098h` 写入是否返回成功、驱动器是否在 OP |
| rc 非 0 且 `bit12` 一直是 0 | 等 `6041h` bit12(Homing attained)超时 | 速度 × 超时的可达距离够不够;开关是否在可达范围内(超时不是停止条件,触发硬件限位才停) |
| `bit3` 立起 | 期间报了驱动器故障 | 查 `603Fh`(§7) |
| `bit13` 立起 | 回零出错位 | 驱动器侧回零配置(斜率 / 参考点开关掩码 `6098h` 一族) |
| 方向不对 | 「正/反」是**电机轴**的正反向,与画布 +X/+Y 是否同向只有现场试一次才知道 | 换另一个方向的方式号;撞着开关还硬回才是真会伤机器的做法 |

**被「停止」中止不是失败** —— 那是人让它停的,界面措辞里有这一条(自检钉着)。

**「回零校准」一次点名两根轴时多出来的两句**(2026-09-24,见 `scan_sweep.md` §33.9):

| 界面原话(要点) | 成因 |
|---|---|
| 「**轴X 轴Y** 回零未发起, 驱动器未写入。」+ 拒因 | 起手预检没过。总线级三道(未连上 / 一份完整 `6064h` 都没取到 / 还有轴在走)不点任何一根的名;逐轴两道(**这一根没收到过完整帧** / **`6041h bit3 = Fault`**)点名那一根。**一根不合格就两根都不动**,所以这句话出现时台上什么都没发生 —— 它描述的不是"失败",是"压根没开始" |
| 「回零结果: 轴X 到位, 轴Y 未到位。**请查 轴Y**。」 | 批级总结, 只报**是哪一根**。这一根**具体**为什么未到位, 在它自己那一句里(`6061h` / `bit12` / `bit3` / `bit13`, 见上表) |
| 「未到位」但**没被点名** | 它是**被对侧带停**的, 不是元凶。与单轴的「被「停止」中止」是同一类: 结局为真, 但**不是它的错** |

最后一行是这张表最要紧的一条。**元凶判定是两趟**(`home_batch_blame`):

1. 先找**第一个 `rc < 0`** 的轴 —— 故障 / 收尾出错位 / 超时 / 帧断 / 起手失败。
   **被「停止」打断的不算**在这里, 那是操作员自己按的。
2. 找不到才走兜底, 而兜底**只在真有「被带停」的轴时才走**, 并且**避开**被带停的那一根。

于是点出来的要么是**自己出事的**, 要么是**把别人带停的**, **绝不会是被带停的那一根**。
点错一根的后果是把一根好轴支去查 —— §33.8 记着这个错真的写出来过(靠推理发现, 不是靠断言)。

**收尾结局**(`home_end_state()` / `home_end_text()`,判据是收尾**那一刻的实测状态**,不是三个
返回码的排列组合):

| 结局 | 含义 | 界面原话要点 |
|---|---|---|
| `HOLDING` | 已使能 + 已是 CSP,停在落点带保持力矩 | 「带保持力矩」。**只有这一档**尾巴上还挂着一个方括号, 说的是"显示坐标 0 落在哪": 偏移为 0 或这一趟是找限位时是 ` (显示坐标已把这里定为 0)`(逐字, 与改造前一样), 生效时是 ` (显示坐标 0 在落点正方向 N pul 处)`, 装不下时是 ` (回零偏移 N pul 未生效: 当前量程 ±M pul)`。三档与它们的成因见 §14 |
| `STRANDED` | 收尾没确认到「已使能 + CSP」→ **电机可能仍带电**,而驱动器不按 CSP 解释 `607Ah` | 「可能仍带电」,并要求断开动力电源 |
| `FAULTED` | 该轴报 `6041h` bit3,停在未使能 | 指到「故障复位」 |
| `NEVER_STARTED` | 前置判据没过,压根没发起 | 闸拦下时现场有故障也不算「这次回零把它搞坏了」 |

## 7. `603Fh` 故障码表

`6041h` bit3 只说「有故障」,**说不了是哪一个** —— 那件事只有 `603Fh` 说。两个来源
(`err_code_from()` **唯一一处**决定挑哪个):映射里有就读过程数据那一个(与 bit3 同帧到达),
不在映射里就走 SDO 回退,而回退**只在 bit3 立起时走**。

| 码 | 含义 | 处置 | ALM 灯红闪次数 |
|---|---|---|---|
| `0x0000` | 无错误 | 码是好的,只是故障位还没清 → 「故障复位」 | 不闪 |
| `0xFF01` | 过流 | 机械卡死 / 堵转;动力线 U V W | 1 |
| `0xFF02` | 过压 | 供电电压;减速设置 | 2 |
| `0xFF03` | 欠压 | 供电与接触器 | 3 |
| `0xFF04` | 动力线报警 | 动力线接线;电机相间 / 对地 | — |
| `0xFF06` | 通讯报警 | 通讯线、干扰源、站号配置 | 6 |
| `0xFF08` | 传感器告警 | 编码器接线与信号 | 8 |

**表外码照实报十六进制**(`0xFF02 (手册之外)`),不猜成「未知故障」。

**两个「不知道」必须分开说**:「还没读到 (正在读)」= 再等一帧就有;「读不到 (SDO 没应答)」=
这一趟读不到了。

**ALM 灯可对账**:面板上数出来的红闪次数就是上表那几个数字。数出来与读到的码对得上,
说明这条 SDO 读的是同一件事;对不上就先别信读到的码。

## 8. 通讯:`WKC` 不足是谁的错

界面只写「过程数据帧连续 %1 帧不足 (工作计数器 %2/%3)」—— 这是**上位机自己看到的**(B 家族),
与驱动器自报的 `0xFF06`(A 家族)是两件事,措辞刻意不共用。

成因(按现场概率):

1. 网线或接头拔了、接触不良、拖链里被磨断;
2. 驱动器侧掉电或掉出 OP(`AL` 状态码见 §9);
3. 某一个从站没进 OP(留在 PRE-OP 的从站不参与过程数据交换,会让**整帧**的 WKC 持续偏短)
   —— 所以 `em_setup` 选的是**总线上全部从站**,不是「前两台」;
4. 干扰(变频器 / 伺服动力线并行走线)。

界面只报「过程数据不完整, 扫描未启动 / 扫描自动中止」,**不写「查网线」** —— 上面四条里
只有第 1 条是网线。

单帧抖动不值得报警:要**连续 10 帧**(30Hz 下约 1/3 秒)才认。

**最长未发帧时间**(`max_gap_ms`)是另一个方向的证词:本程序自己最长多久没发出一帧。
它与 WKC 不足同时出现 = 问题在这一侧的调度或阻塞命令上,不在线缆上。

### 8.1 停顿已过去、从站还没回来(2026-09-23)

上一条只说了一半。现场实机那条是真的**停顿**:空闲无人操作时,本程序**最长 1657 ms 一帧都没
发出去**(超 50 ms 共 12 次)。后果不是"漏了几帧",而是**从站不回来了**:

上位机停顿 1.6 s → 两台驱动器的 SM 看门狗动作(`AL` `0x14` = SAFE-OP + 错误位,
状态码 `0x001B`,见 §9)→ 从站停止过程数据交换 → `WKC` 恒为 2/6 → 各轴 `mirror_ok` 降 0
**且再也升不回来**(它只在收到完整帧时置位)→ 复位/使能全部被有效地拒,
**唯一的回程是「断开 → 重连」**。

所以有几句话是**分开的两件事**,不许互相冒充:

| 局面 | 该说的 | 不许说的 |
|---|---|---|
| 帧不足、`6041h` 是陈旧值 | 「6041h 是**陈旧值**,判不了有没有故障,**一个字节都没写**」,处置指向通讯 | 「无轴报故障(6041h bit3 均为 0)」—— 那是把"判不了"说成"没有",与同一块屏幕上刚说过的"陈旧值"直接打脸 |
| 帧不足、点「使能」失败 | 「这次失败**与驱动器的故障位、限位无关**」 | 「请确认 6041h 故障位与限位状态」—— 那句话的前提是"我看得见驱动器状态" |
| 本机停顿造成的静默 | 「是**这台机器自己**的停顿,不是从站的问题」,处置指向电源计划 / 网卡节能 | 去动从站的 `AL` 寄存器 |
| 自动恢复**动手前**那句 | 「本机已连续 N 帧按时发出,而过程数据帧仍连续 M 帧不足」—— 两件都真查过,带数字 | 「从站仍不在 OP」—— 判据里**没有一条读 `AL`**,而那句话说出口之后下一句就可能打脸 |

**归因必须分两份**:`max_gap_ms`(全程最长,含**本程序自己的命令**造成的静默 —— 复位/使能/
回零期间 SOEM 的 SDO 事务一帧都不发)与 `max_gap_self_ms`(其中自家那一份)。自动重请求 OP 的
触发**只看净的外部停顿**:不分开的话,我们自己一次使能造成的 1 秒静默会被读成"这台 PC 在卡"。

自动重请求 OP 的判据(`ecatcmd::recover_verdict`)量的是**上位机**够不够稳 ——
即连续多少帧**按时**发出去(`gap_ok_run`),**不是** WKC。用 WKC 会永远不动手:从站一旦掉出
OP,WKC 就恒为 2/6,那个数永远涨不上去。三种"不动手"的局面(没答话 / 停在 INIT / 混合局面)
一个 `AL` 字节都不写,只喊人;`RECOVER_MASTER`(眼下这一帧就迟到了)压过
`RECOVER_GIVEUP`(本会话试满了)—— 顺序是内容,**先说根因**。

**动手要两个条件同时成立,各管一头**(2026-09-23 第一次实跑补上第二条):
`recover_verdict` 问"本机够不够稳、还有没有机会"(上位机侧)与 `recover_bus_broken`
问"总线是不是真的需要救"(总线侧)。少了后者,一条**健康**的总线在连上约 2 秒后就会被点着 ——
第一趟触发时它自己紧接着报「所有从站的 AL 都在 OP」。`RECOVER_MASTER` 不受总线那道闸管。

**触发前那句话只许说真的查过的事**。曾经写的是「本机已经稳了一阵子而**从站仍不在 OP**」,
而判据里一条读 `AL` 的都没有 —— 同一段日志里它下一句就是「所有从站的 AL 都在 OP」。
现在的原话是「本机已连续 %1 帧按时发出,而过程数据帧仍连续 %2 帧不足」:两件都真的查过,且带数字。

**`AL` 状态字 bit4 是闩锁,清它要单独一步**:写 `当前那一级 | ACK`,然后每圈照常发过程数据
等它自己消失,再往上爬。把它与目标级(OP)一起写、或者清错期间断帧,都会让从站把这次
看门狗告警再分一次 —— 症状是"重请求了但没上去",而那看起来像"这个功能没用"。

### 8.2 节拍一直慢着(2026-09-24)

§8.1 那把尺(`max_gap_ms`)量的是**最长一次停了多久**,而且是离群点判据(> 50 ms)。它有个
盲区,这次在真总线上查出来了:**节拍均匀地慢下来,它看不出来。**

现场症状是「连上、放着不动,过一会儿断连」。实机复现(真总线、进 OP、只喂帧不发命令,
一趟 30 分钟)量到的正是这个盲区:`max_gap_ms` 那一整趟记到的是一个 **79 ms** 的离群点,
而**同一趟里帧周期是 15.8 ms(全程)** —— 它报出来的那个数与"节拍"根本不是一回事:一圈
均匀地慢下来时,它要么什么都不记(没有超过 50 ms 的那一次),要么只记下偶然的那一两次,
**屏幕上没有任何一个字解释"每一帧都迟到了"**。

病态那趟不是漏了几帧 —— 是**每一帧都迟到**:上位机的节拍 `em_sleep_ms(2)` 实际睡掉一个
系统 tick(15.6 ms),一圈慢 8 倍(正常 2.5 ms)。驱动器每 2 ms 就该收到一帧,一直这样喂,
它的 `SM` 看门狗迟早动作,接着就是 §8.1 那条链(掉出 OP → `WKC` 恒 2/6 → `mirror_ok` 降 0
且升不回来 → 只能重连)。

**节拍慢的根因是 `Sleep()` 的粒度**:它由本进程有没有"1 ms 定时器精度请求"决定(Windows 10 2004 起
该请求是 per-process 的),而 Windows 会把没人操作用的后台进程的精度请求丢掉。处置在
[`scan_sweep.md` §34](scan_sweep.md) —— 一句话:节拍换成高精度可等待定时器,并在工作线程
起手拒绝省电节流。

**另外加一把尺:平均帧周期。** `BusTelem::period_avg_ms` = 最近 64 帧的平均;
`ecatcmd::cadence_slow` 判它超过 3 倍圈期。

| 界面 | 原话 |
|---|---|
| 状态栏(`scan` 与 `hmi` 同一句) | 「WKC 6 / 期望 6 · 帧周期平均 16 ms (上限 6 ms)」 |
| 通讯横幅(帧不足那一刻) | 多一句「本程序帧周期平均 16 ms (上限 6 ms)。」 |

**它与 `max_gap_ms` 是两个数,不许互相顶替**:那个是"最长一次"(离群点),这个是"整条节拍
多快"。同一趟 30 分钟里前者说 79、后者说 15.8,谁也替不了谁。

**上限取 3 倍圈期而不是写死一个数**,实测把它夹在中间:正常 2.5 ms 之下、病态 15.9 ms 之上,
离两边都远(2.4 倍 / 2.6 倍)。

**它不并进 `comm_bad`**:那条线会去点自动重请求 `OP`,也就是往从站的 `AL` 寄存器里写字节;
而"本机节拍慢"还不到该动寄存器的程度,它该做的是让人看见。所以状态栏那一句**不受**"出过事
才常驻"那道闸管 —— 等 `comm_bad` 立起来再说,就已经断连了。没量到(< 1 窗)与正常一样,
一个字都不出。

## 9. `AL` 状态码(从站侧)

表照 SOEM 的 `ec_ALstatuscodelist` 手抄(自检不链 SOEM,所以判据那边自带一份)。
只抄这台机器真可能撞上的那几条,认不出的回落到十六进制。

真正常见的:

| 码 | 含义 | 备注 |
|---|---|---|
| `0x0011` | 被要求的状态迁移不合法 | 一般是主从状态不同步 |
| `0x0017` | 同步管理器配置不合法 | 映射 / SM 设置 |
| `0x001B` | 同步管理器看门狗(主站喂帧超时) | **与 `603Fh = 0xFF06` 说的是同一件事**,一个在从站侧报、一个在驱动器侧报 |
| `0x0020` | 从站需要冷启动 | 断电重启 |
| `0x0034` | DC 同步超时 | 本程序**不上 DC**(SM 同步 / 自由运行) |

**`1C32h:01` 报 2(DC 同步)而本程序不发 SYNC0** 是一条单独的坑:那类报警与上位机发不发帧
无关,需要另配驱动器。连接时控制台会打出 `1C32h:01/:02` 与 `2217h` 的读数(都在 `consoleNote`
里,不在界面上)。

## 10. 软件侧的确定性错误(与控制台 / CSV 有关)

这几条不是硬件问题,成因单一,但界面也只用一句话:

| 界面原话 | 成因 |
|---|---|
| 「未到位: 下发目标 … 始终未进入容差」 | 机械卡住 / 被限位挡住 / 目标被量程夹掉。第三种最隐蔽:超出量程的目标会被**静默夹掉**,不报错 |
| 「区域超出量程」 | 网格最远点超出当前软量程。参数刚改过时量程要等工作线程转一圈才跟上,此时启扫会撞上这一条 |
| 「该 CSV 采于另一次零点」 | 回零与「设为区域中心」都会**搬动**零点(重新连接不会)。同一个坐标可能已指向另一个物理位置,接着扫会把两份数据拼在同一张图上 |
| 「区域 / 分辨率 / 每 mm 脉冲数已改动」 | 单点重测是把一行**追加**到那个 CSV 里;几何变了以后 `(ix,iy)` 已不是文件里那一点 |
| 「点数 %lld 超出上限」 | 上限是一道资源闸(见 `scanplan.cpp` 的点数上限一节)。常见成因是分辨率少打一位 |
| 「收尾时未能确认所有轴已失能」(模态,`hmi` 与 `scan` 同一句) | 收尾过程中总线已经掉了:驱动器还带着力矩,而主站已经没有通道去撤它。**软件到这一步没有补救手段**,所以那一句只留「请立即断开动力电源」—— 这是全程序唯一一条"别信软件"的提示 |

## 11. 改界面提示语时的检查清单

1. 这一句说的是**状况**还是**成因**?成因 → 写进本文,界面上不留。
2. 有没有替操作员决定下一步?有 → 删掉,除非真的只有一条出路,那就写成一句「请……」。
3. 限位开关的词是不是「触发 / 未触发」?
4. 数字与寄存器是不是原样(`6041h bit3` / `0xFF02`)?
5. 长度还在 [`scan_sweep.md` §26](scan_sweep.md) 那张表内吗?
6. 改到 `hmi/ecatworker.h` 的 `ecatcmd::*` 函数时,`scan/selftest.cpp` 里钉着那些词 ——
   断言允许在**同一层**上机械调整(比如「都没压着」→「都没触发」),但**钉住的判据本身**
   (必须点名的码 / 必须出现的出路 / 不能出现的猜测)一条都不许删。

## 12. 「测量原点宽度」(2026-09-28)

入口是回零折叠块里那一个按钮 + 一行读数。它**一趟两段**: 段 1 就是「回零校准」那一趟
(方式 24, 两根同时), 段 2 从那个落点顺着**正向**慢速走过去, 每 2 ms 采一次 `60FDh` bit2
看它翻两次, 两个边沿之间跨了多少脉冲就是读数。设计与安全包络在
[`scan_sweep.md` §35](scan_sweep.md); 本节只说**屏幕上那些字背后是什么**。

段 1 的所有话与 §6 那份**逐字相同**(它本来就是一回事), 这里只写 §6 没有的那些。

### 12.1 按下之前: 灰着、没动静、压根没发起

| 界面现象 | 成因 |
|---|---|
| 按钮**灰着** | 与「回零校准」**同一套判据**(未连上 / 没收到过完整 `6064h` / 有轴在走 / 两轴各自的 `6041h bit3 = Fault` / 镜像不完整), **再叠加一条: 两根的 `60FDh` 都得读得到**。`60FDh` 不在生效 TxPDO 里时 bit2 恒为 0, 那一趟会一路走到行程上限、报出一句「一路走完都没等到原点信号」—— 而真正的原因是**根本没在采**。让按钮先按不动, 比跑完一趟再解释好 |
| 弹一句「**扫描进行中, 测量原点宽度不可用。**」 | 扫描循环也在发 `607Ah`, 谁也不该和谁抢。先停扫描 |
| 状态栏一行「**轴X 轴Y 测量原点宽度已下发 (速度 N pul/s)。**」, 然后**没有然后** | 这是**回音, 不是承诺** —— 命令还在队列里没被接走(前一条命令占着队列 / 这条命令被那道闸拦掉)。真跑起来的话, 最长 33 ms 之后它就被「正在测量原点宽度…」那条横幅盖掉 |
| 状态栏一行「**轴X 未发起, 驱动器未写入。60FDh 读不到 → 采不到原点信号, 拒绝测量。请勾选「让 60FDh 进 TxPDO」并重新连接。**」 | **不是失败, 是"压根没开始"**: 起手预检没过。总线级三道 + 逐轴两道(`home_batch_refusal`)之后**新加的一道**, 专为这一趟(找限位那道
`60FDh` 否决只管 17/18, 这一趟走的是 24, 走不到它)。它在 `em_disable()` **之前**判 —— 那是真的一次撤保持力矩(竖直轴会滑), 所以拒绝时两台驱动器都还没被动过。不合格的两根会**一起点名**(「轴X 轴Y」) |

### 12.2 那一行读数(四个态, 两两不同)

| 读数 | 意思 | 该怎么办 |
|---|---|---|
| 「**轴X 未测量**」 | 这台开机之后**还没跑过**这一趟 | 要那个数就按一下按钮 |
| 「**轴X 测量中**」 | 这一根正被**段 2** 持有。**段 1 期间不是这一态** —— 那一段说的是「回零中…」, 这一行此时显示的是上一次那个数(或「未测量」) | 等它走完, 或按「停止」 |
| 「**轴X 12345 pul**」 | 量到了。它**一直留着**, 直到下一次量(或断开重连) | 直接抄走 |
| 「**轴X 未测得 (现象)**」 | 跑过了但没量到。括号里是现象, 出路在状态栏那一句里 | 见 §12.3 |

「未测量」与「未测得」**必须分得开**: 前者要人按一下按钮, 后者要人去查开关 —— 混成一句,
人就不知道这一趟到底是没跑还是没跑成。

### 12.3 「未测得」的十一种现象

现象与出路是**两句分开的**: 读数那一行只放得下现象, 出路在状态栏(`span_axis_note`)里跟着
现象一起说。**出路只许一句「请……」**, 没有出路的那两条(自己按的「停止」/ 被对侧带停)
就只报现象。

| 现象(读数行里那句) | 出路 | 背后最可能是什么 |
|---|---|---|
| 一路走完都没等到原点信号 | 请检查原点开关的接线与位置后再试 | 开关没接 / 反相 / 落点已在远端边沿之外; 也可能是 `60FDh` 的 bit2 映射错了位 |
| 进了原点信号就再没出来, 已到行程上限 | 请检查该开关是否一直有效后再试 | 开关卡在有效位, 或信号有效区间比量程还宽。**退避那一段走满 2 万脉冲还在信号里也走这一句** |
| 被「停止」中止 | (没有出路 —— 那是操作员自己刚做的动作) | 「停止」按钮, 以及断开收尾那条路 |
| 超时时间到还没量完 | 请把回零速度调大或把超时调长后再试 | 超时框那个值只对**段 2** 计时(段 1 有它自己那一套); 走得慢 + 超时短就会撞上这一条 |
| `6041h bit3 = Fault` | 请先「故障复位」 | 驱动器自己报了故障, 码在 `603Fh`(§7) |
| 这一根掉了使能 | 请重新「使能」后再试 | 段 2 全程不需要重下使能, 掉了就是驱动器侧的事 |
| `60FDh` 中途读不到了 | 请勾选「让 60FDh 进 TxPDO」并重新连接 | 映射掉了或链路抖动(§2)。**起手时就能判到的那一半在 §12.1 那道闸上**, 这是中途变假 |
| 轴没跟着走 | 请检查限位与行程后再试 | 目标被"实际位置 + 2000 脉冲"夹住并持续 50 圈。撞限位、`2204h` 超程停车、卡住都会走到这里 —— **成因不写进界面** |
| 总线已断开 | 请重新连接后再试 | 掉出 OP / 链路没了 |
| 被另一根轴带停 | (没有出路) | 另一根出事时**同一圈把它也停下**(与回零会话"两根一起停"同语义)。**它自己没毛病** |
| 目标位置下发不出去 | 请检查过程数据映射后再试 | `em_csp_set_target()` 返回 -1。这一条**只在过程数据映射缺项时**出现, 与"轴没跟着走"是两件事 |

十一种里,**两种没有出路**: 自己按的「停止」不给人指路; 「被另一根轴带停」的那一根本来就没
毛病(要找原因看**另一根**那一句); 剩下九种各给一句「请……」。


### 12.4 段 2 期间屏幕上的字

| 位置 | 字 | 为什么是这一句 |
|---|---|---|
| 横幅 | 「**轴X 轴Y 正在测量原点宽度, 按「停止」可立即中止。**」 | 与回零那条横幅**分开写**: 一个在量边沿距离、一个在找开关, 共用一句必然说错一件。**段 1 期间挂的也是这条** —— 段 1 本来就是这次测量的第一步 |
| 那八个回零/找限位按钮 | 「**测量中…**」 | 段 2 里这一根干的事**已经不是回零了**。只改**这一根**的按钮(判据是逐轴的), 另一根写什么由它自己的状态决定 |
| 红色横幅(限位) | **照常弹、不压制** | 找限位那套豁免("这一趟的目的就是撞那个开关")**只覆盖 17/18**。段 2 的目的是原点信号, 所以段 2 里限位信号真置起了, 那条红横幅说的事**是真的** |

### 12.5 量完之后

| 界面原话 | 意思 |
|---|---|
| 「**轴X 原点宽度 12345 pul (停在远端边沿, 显示坐标 6789)。**」 | 一根一句, 发在状态栏(逐轴那两句里只剩最后一句)。**必须带上"停在哪儿"** —— 段 2 不重锚零点, 停下时的显示坐标不回到落点, 不说清人就以为程序坏了 |
| 「**测量结束: 轴X 12345 pul, 轴Y 未测得。**」 | 两根时**再补一句批级总结**: 状态栏是覆盖写, 逐轴那两句里只剩最后一句, 而"是哪一根没量到"正是最要紧的那条。它**不出原因的全文**(那在两轴各自那一句里), 只报数与"未测得" |

**量完停在远端边沿, 不是 0** —— 这是设计如此(段 2 不重锚零点, 否则就把这次测量本身想量的
东西抹掉了)。想回 0 再按一次「回零校准」。

> **2026-09-28 补(§38)**: 上面那个「显示坐标」是**宽度 − 回零偏移** —— 段 2 全是相对运算,
> 偏移不影响它量出来的**宽度**本身, 只影响印出来的那个坐标。段 1(方式 24 回零)的落点也从
> 0 变成了 **−偏移**(缺省 −75000)。界面上那一行 tooltip 因此写成「显示坐标**不回到落点**」:
> 偏移正好等于信号宽度时, 终点显示坐标**正好是 0**, 原来那句「不再是 0」在那种机器上是假话。

### 12.6 与 §6 的关系

- 段 1 失败 → 走的就是 §6 那一整套(含「回零未发起」与「回零结果: …」两句批级总结), **一个字都没改**;
  段 1 有任何一根没到位, **段 2 就不会开始**(判据是"每一根都 ATTAINED"), 于是也**没有**测量读数。
- 段 2 失败 → 只有 §12.3 那些句子, **不重复** §6 的收尾结局那一套(段 2 不写 SDO、不切模式、
  不失能, 没有"可能仍带电"那一格)。
- 两段的分界在屏幕上**只由横幅与按钮文字区分**(「回零中…」→「测量中…」), 因为两段说的是
  同一根轴、同一个会话、同一趟按钮。

## 13. 功率计打不开(2026-09-28)

**界面原话**:

- **横幅**:`功率计打开失败, 请按「重试」。`
- **状态行**:`功率计未打开 · ` 后面跟着具体原因(实际那一格以源名开头, 例如
  `Ophir 功率计 (PD300R/Juno+) · 未打开 · 未找到 Ophir USB 设备。…`)。**上面那些原因只有它
  一个落点; 而打开成功时这一行整行不显示** (2026-09-28 起, 见
  [docs/scan_sweep.md](scan_sweep.md) §37.8) —— 那一行另一半 (`已打开 · <设备摘要>`) 里的字
  屏幕上别处全都有, 说了两遍。

打开功率计**全仓库只有一条路** —— `ScanWindow::openMeter()`(构造函数那一次与「重试」都走它)。
它先过**两道不建 COM 对象、不碰 USB 的预检**(所以随时可调, 不必让界面白冻 12 秒再说同一件事),
两道都过了才进 `OphirMeter::open()`(阻塞: COM 同步开 USB 设备, 正常几百 ms)。预检**查得出来
不等于打得开** —— 表头没插、通道上没探头、别的程序占着, 这三样预检都过得去, 失败从那一路自己
那句话里出来。

### 13.1 两道预检(查得出来就根本不去碰设备)

| 状态行里的原因(原话) | 判据 | 出路(界面已写在这一句里) |
|---|---|---|
| `未找到 OphirLMMeasurement COM 对象。请安装 Ophir StarLab。` | 注册表里没有 `OphirLMMeasurement.CoLMMeasurement` 这个 ProgID(`OphirCom::isRegistered()`) | 装 Ophir StarLab |
| `功率计组件注册不完整。请重装 Ophir StarLab。` | ProgID 在, 但 CLSID → `InprocServer32` 的 dll 路径读不出来, 或从那个 dll 的资源里读不出 typelib(`OphirCom::isAvailable()`) | 重装 Ophir StarLab |

### 13.2 `open()` 自己回的那几句(按可能性排)

| 状态行里的原因(原话要点, 全文见 `scan/ophirmeter.cpp`) | 最可能是什么 | 查什么 |
|---|---|---|
| `未找到 Ophir USB 设备。请确认 Juno+ 已插好, 并在 StarLab 中确认该表头是否被识别; …` | 没插 USB 表头(Juno+), 或线 / 供电 / Windows 没认到 | 先在 StarLab 里看认不认这个表头(原话点了这条); StarLab 里也读不到功率, 问题在硬件或驱动 |

| 原话要点 | 最可能是什么 |
|---|---|
| `创建 Ophir COM 对象失败: <码>` | 对象注册项在, 但 `CoCreateInstance` 起不来(这份安装被搬过 / 权限) |

| `枚举 Ophir USB 设备失败: <码>` | 枚举那一步在驱动层就失败了(与"枚举成功但一个设备都没有"是两句话) |
| `读取表头信息失败: <码>` / `读取探头信息失败: <码>` / `启动测量失败: <码>` | 设备在, 但配置 / 启动某一步失败。括号里的码查 `OphirCom::errorText()` 那一张表(手册 Error Codes 的译文) |
| `在该线程上初始化 COM 失败: <码>` | 采集线程上 `CoInitializeEx` 失败。服务端是 Apartment 模型, 之后每一次 COM 调用都得在那个线程里 |

### 13.3 「重试」做的是什么

它就是**再走一遍 `openMeter()`** —— 唯一的打开入口, 没有第二条路。成功之后它做两件事: 把那一路
连续读数的**未决请求作废**(`m_mlog->stop()`), 采集由下一拍 `refresh()` 自己拉起来(采集常开,
源开着就该在采)。

所以它也是**「采集卡死」那条路唯一的出口**: 一个**已经打开、只是卡死**的表头(发了请求没人回,
`MeterLog` 超时之后刻意停在原地等), 按「重试」连 COM 都不走 —— `OphirMeter::open()` 见已打开直接
返回 true, 真正救回来的是把卡住的未决请求作废这一步。**这两件事不许混成一句。**

「重试」露出来的两个时机是**打开失败**与**采集卡死**(判据在 `refreshMeterPanel()` 一处)。

### 13.4 为什么只留 `0x8002801D` 这一个码

本机 typelib 的注册项是坏的(版本号是字面量 `a.a`), 历史上 `IDispatch::GetIDsOfNames` 一路都返回
`0x8002801D`(TYPE_E_LIBNOTREGISTERED)。现在代码**绕开了注册表**, 改成从服务端 dll 的资源里
`LoadTypeLibEx` 读类型库(`scan/ophircom.cpp` 的 `loadInterfaceTypeInfo`), 所以这个码**正常情况下
不该再出现**; 真出现就说明 dll 本身坏了 / 被换过。

这个码留着是因为它是「请重装 Ophir StarLab」这条出路**唯一的判据** —— 没有它, 那句话就只剩猜测。

### 13.5 三个下拉框的选项表为空, 不是打不开的原因

面板上的**波长 / 量程 / 模式**三个下拉框是**设备报什么就填什么**, 一个都不写死(探头不同, 能选的
波长与量程就不同)。选项表为空是**正常的** —— 手册说某项对这个探头不适用时 `options` 为空、
`index` 为 -1; 那时那个框自己不可改(放开就是个假控件), 但**设备是打开的**。这一条与"打不开"
是两回事。

### 13.6 「设备不接受这个波长」(2026-09-28)

**界面原话**: 红横幅 `改功率计配置失败: 设备不接受这个波长。请换一个值。`(前面那半句是
`configFailed` 那条路统一加的)。

**这一句说的是什么**: 面板上「添加波长」那个旋钮(330-1100 nm)→ 工作线程**停流** →
`AddWavelength(通道 0, nm)` → **把波长表读回来**(`GetWavelengths`)→ 在读回来的那一份里按 nm 找
→ **没找到**。所以它的意思是"**表里没有它**", 而界面那一步**什么都不改**: 下拉框不多出这一项、
CSV 里也不记它 —— 让一个没生效的波长进文件, 那份文件就开始说假话。

成因(按可能性排):

| 最可能是什么 | 为什么 | 查什么 |
|---|---|---|
| 这个值**超出这台探头的响应范围** | 330-1100 nm 是**上位机给的宽范围**(`k_wl_min_nm` / `k_wl_max_nm`), **与探头无关**; 设备那张表是**探头的能力表** | 探头标签上的波长范围; 那张表里本来有哪几档 |
| 表头固件不接受这个值 | `AddWavelength` 自己返回失败(那句横幅里是 **COM 的原话**, 不是本程序写的), 或者写进去了而固件的表不认 —— 有的型号只收它自己那张表里的档位 | 在 StarLab 里手动加一次, 看它认不认 |
| 通道不对 | 全仓**写死通道 `0`**; 探头插在别的通道上时, 往通道 0 写要么失败、要么写进一张空表 | 表头上有几个通道、探头插在哪个 |

**"写失败"与"读回没有"是两件事**, 界面上落在三句不同的话里: `AddWavelength` 那一步失败时横幅
里是 **COM 的原话**; 读回那一步失败时是 `写入后读回波长列表失败: …`; 上面这一句只在
"没报错、而读回来的表里没有"时出现。要分清看控制台那一条。

**与 §13.5 不是一回事**: §13.5 说的是"**选项表为空也能打开**", 这一条是"**表里没有这个值**"。
两件事都**不是打不开**。

> **这一句 2026-09-28 晚起在界面上出不来了**: 「添加波长」那一行按用户要求藏了起来
> ([docs/scan_sweep.md](scan_sweep.md) §37.12), 没有入口就没人能触发它。**留着这一节是因为
> 那条路还在代码里** (`OphirMeter::addCustomWavelength` 与那个槽一个字节没删, 自检还在钉它的
> 解析函数) —— 哪天把那一行放回去, 这一节就又是现成的排查材料。

### 13.7 「未找到上次那台功率计」(2026-09-28)

**界面原话**: 状态行那一格(`功率计未打开 · … · 未找到上次那台功率计 (<序列号>)。请确认它已插好。`)
—— 与 §13.2 那几句走的是**同一条路**(`OphirMeter::open()` 的失败原因), 判据是"`scan.ini` 里
记的那一台**这一次枚举没看到**"。

上一次用的是哪一台记在 `scan.ini` 的 `meter/serial`(`scan/scanprefs.cpp`), **在 `open()` 之前**
交给工作线程。枚举(`ScanUSB`)回的是**序列号**, 所以这一句能把那个串直接写出来 —— 这一句用的
判据**始终是序列号**: 面板「设备」下拉里那一项的字现在虽然详细得多(「探头 (s/n: …) · 表头
(s/n: …)」, 见 [docs/scan_sweep.md](scan_sweep.md) §37.9), 但"记的是哪一台"与"比的是哪一台"
都是那个串。

**指定了哪一台就只打那一台, 不在就快失败** —— **不许悄悄退到第一台**: 两台表头接在同一个台面上
时, 悄悄换一台就是拿另一个探头的数据当这一个用。

成因(按可能性排):

| 最可能是什么 | 为什么 | 查什么 |
|---|---|---|
| 那台**没插好 / 被拔了** | 最直白的一种。**线换口不影响它** —— 序列号是表头自己的 | USB 线与供电; Windows 认不认这台设备 |
| 台面上**换了一台表头** | ini 里记的是上一台。它是**操作习惯**那条记忆, 不会自己跟着设备变 | 面板「设备」下拉里现在有哪几台 (每一项写的是「探头 (s/n: …) · 表头 (s/n: …)」, 见 [docs/scan_sweep.md](scan_sweep.md) §37.9), 与 StarLab 里看到的是不是同一台 |
| 那台枚举不出来, **而别的表头还在** | 单台时这一句本来是 `未找到 Ophir USB 设备`; 有第二台在就变成这一句(列表非空、里面没有它) | 那台的驱动 / USB 层 —— 在 StarLab 里认不认 |

**出路**: 那一句里写着「请确认它已插好。」; 若台面上确实换了设备, 从「设备」下拉里**直接选现在
这一台**就行(切换即重开)。这两句都不是"步骤", 是这个面板上现成的两个动作。

**热插拔这里有一条已知限制**: 枚举只发生在 `open()` 里(首次打开 / 切换设备 / 「重试」), 所以
**开着的时候再插一台看不见** —— 那种情形要重开程序(不加「刷新」按钮是刻意的, 见
[docs/scan_sweep.md](scan_sweep.md) §37.6)。

> **2026-09-29 补**: 上面这句里"**要重开程序**"有一条**已经修掉的**来源 —— 从前**插上表头再按
> 「重试」**本身也是坏的(能连上、读不到数), 见 §13.8。现在按「重试」就是真的重开一次会话。

### 13.8 「按了「重试」连上了, 但读不到数」(2026-09-29 修掉的一条)

**界面原话**: 那一框底下的黄字 `请求无响应, 采集等待中。`, 加一条红横幅, 加露出来的「重试」
—— 与**表头真的卡住**时屏幕上一模一样 (见 [docs/scan_sweep.md](scan_sweep.md) §36.8)。

**怎么分辨它和"表头真卡住"**: **再按一次「重试」**。真卡住的那个, 这一按会把卡着的未决请求
作废、重新发一个, 表头只要还活着就会有数回来; 这一条**按几次都没用**, 那行黄字与数一动不动 ——
设备是**真打开的**(枚举、读表头信息、启动测量都成功了), 只是**没有人再去问它**。

**成因**(2026-09-29 之前): 工作线程**在报出"打开成功"之后立刻自己收摊了**。"该收摊了"那个标志
(`quit`)只被 `close()` 置 1, 而 `open()` **不清它**。于是这条路是坏的:

1. 开程序时表头没插 → `open()` 失败, 它照着 `close()` 收尾 → `quit` 从此停在 1;
2. 插上表头, 按「重试」→ 设备**真打开了**, `open_ok` 是 true, 状态行写着已连接;
3. 新线程一进 `while (!quit)` 就**跳过整个取数循环**, 停流、关设备、退场;
4. 之后每一个读数请求都没人接, `MeterLog` 等不到回话 → 黄字 + 红横幅 + 「重试」。

**只有重启程序能好** —— 那是唯一能让状态重新构造、把 `quit` 变回 0 的路。

**「切换设备」是同一条路**(它先 `close()` 再 `open()`, 见 §13.3), 症状一样: 换过去之后再也不出数。

**现在怎么修的**: `open()` 在起线程之前把 `quit` 与"有没有未决请求"一起清回 0 —— 两个标志都是
"给**当前这一次会话**"的。自检里插了一根钉子: 对着真表头**连着开两趟**(第二趟就是"重试 / 切换设备"
那条路), 每趟都要**恰好吃到一个读数**。这根钉子**必须插在真表头上** —— 没插表头时第二趟 `open()`
是直接失败的, 走不到这条路上 (那条"失败两次都要干净"的路在另一个用例里)。

**为什么留着这一节**: 这一条**已修**, 但它给"按了「重试」没反应"这一类现象留下了一条现成的判据
——先分辨"线程死了"还是"表头真卡住", 两者屏幕上一模一样, 而处置完全不同。

## 14. 「回零偏移未生效」(2026-09-28)

**界面原话**(回零结论句第 2 行的末尾, 只在结局是 **`HOLDING`** 时才有这一截):

```
轴X 正向回零 (方式 24): 到达原点 (rc = 0)。
已切回 CSP 并保持使能, 停在落点带保持力矩 (回零偏移 75000 pul 未生效: 当前量程 ±1600 pul)。 […]
```

**它说的不是"回零失败"** —— 回零这一趟**跑完了、到位了、带保持力矩**。它说的是
"**这一趟没搬零点**": 显示坐标 0 还在落点上(即改造前的行为), 屏幕上落点读 0 而不是
−75000。所以要查的不是回零, 是**为什么装不下**。

判据是 `ecatcmd::home_off_fits(off, range)` = `range > 0 && off <= range`(闭区间),
`range` 是**起手那一刻**的 `m_range`; `%1` 是界面框里的数, `%2` 是那个量程。两者都在句子里,
所以这一句自己就够定位了。

成因(按可能性排):

| 最可能是什么 | 为什么 | 查什么 |
|---|---|---|
| **脉冲当量被调小了** | 量程是**算出来的**, 不是拍的: `autoRangePul()` = `ceil(max(区域半宽 + 1 mm, 画布半宽 16) * 脉冲当量)`, 下限受**画布半宽 16 mm**兜着 (`scan/scanplan.h`)。脉冲当量一降, 量程就跟着降 —— 75000 pul 这个**常数**于是相对变大。门坎: 量程 ≥ `16 * 脉冲当量`, 所以缺省的 75000 要装得下, 脉冲当量得 **≥ 4688 pul/mm**(缺省 50000); 脉冲当量下限 100 时量程只有 ±1600 pul | 面板上那一行「1 mm = N 脉冲」。反推: 要让 75000 pul 装得下, 量程(`±%2` 那个数)必须 ≥ 75000 |
| **扫描区域被改小了** | 公式里 `区域半宽 + 1 mm` 那一项变小 → 量程变小。但**画布半宽那条下限(16 mm)兜着**: 区域改到再小, 量程也不会低于 `16 * 脉冲当量`, 所以**光改区域够不到**这一档 | 区域 X/Y 两个框 (多半不是它) |
| 界面上的「回零偏移」被填得过大 | 它自己就是 `%1`。上限是 `HMI_HOME_OFF_MAX`(= `HMI_RANGE` = 500000 pul), 而真正的上限是**当时的量程** | 展开项里那两个框, 与结论句里的 `%2` 对一下 |
| 量程压根没被量到(`range <= 0`) | 起手那一刻量程未知时不搬 —— **不知道就别赌**(与 §29 那条沿用判据同一条规矩) | 这种情况一般出不了: 界面在连接时就会 `postRange`, 状态栏也会说"量程已从 … 改为 …" |

**出路**: 句子本身不给「请……」—— 因为这里的处置分两种情形, 而哪一种取决于**现场要什么**:
想把零点搬到 75000 处, 就把量程放大(调脉冲当量或区域); 这一趟本来就不打算搬, 那就什么都不用做,
读数 0 是**正确的老行为**。所以界面上只说事实, 不说下一步。
[`docs/scan_sweep.md`](scan_sweep.md) §38 写的是这一项的设计与交互。

### 14.1 与另外两句容易混的

| 屏幕上看到 | 说的是 |
|---|---|
| ` (回零偏移 75000 pul 未生效: 当前量程 ±1600 pul)` | **找原点**这一趟**本来该搬**却装不下 → 本节 |
| ` (显示坐标 0 在落点正方向 75000 pul 处)` | 搬成功了, 这一句是"搬到了哪" |
| ` (显示坐标已把这里定为 0)` | 偏移为 0, **或者这一趟是找限位**(17/18) —— 两种情形**同一句话**, 而且它与改造前的原话**逐字相同** |

**"填了 75000 却按了找限位"不会走到本节这条路上**: 那种情形判据里 `is_limit` 那一档排在
前面, 出来的是 ` (显示坐标已把这里定为 0)`。这是刻意的 —— 找限位不叠加偏移是**设计**,
不是"没生效"; 把它报成"未生效"就是凭空造一个故障出来。

**偏移为 0 时这三档一句都不会出现**(尾巴上是那句逐字不变的「已把这里定为 0」)。

### 14.2 这一条与 §12 的关系

「测量原点宽度」的**段 1** 就是方式 24 回零, 所以它也吃这条偏移。段 1 装不下时:
段 1 的结论句照本节写「未生效」, 而**段 2 照跑** —— 它量出来的**宽度**与偏移无关(段 2 全是
相对运算), 只是读数那一行印出来的**终点显示坐标**从「宽度」(偏移 0)变成「宽度 − 偏移」。

## 15. 零点是从 `scan.ini` 恢复的 (2026-09-29)

**界面原话**(连接那一刻的横幅, `scan` 独有):

```
零点从 scan.ini 恢复 (程序重启未重设)。滑台当前显示在 (-75000, 0) pul。
```

**它说的是一件对的事**: 关程序之前那份零点还在, 现在把它接回来了 —— 同一块屏幕上,
关之前与重开之后读到的**是同一个物理位置**。这一句**只在"从盘上捡回来"的那一次出现**
(报过一次就不再报), 而"本次运行里断开重连"那种沿用说的是另一句
「沿用上次零点 (本次连接未重设, …)」。

**它与 `hmi` 无关**: `hmi` 从不调 `setKeepOrigin`, 它那一侧"连接那一刻即零点"没变。
所以这句话**永远不会出现在 `hmi` 上**。

### 15.1 什么时候它是对的, 什么时候它是可疑的

| 屏幕上的数 | 这一句话对不 |
|---|---|
| 接着关之前那个数(量程之内) | **对** —— 正常用法(滑台没被动过, 驱动器也没断过电) |
| 接着关之前那个数, **但有人趁这段时间挪过滑台** | 数**不是**它刚才停的那个 —— 滑台现在被**静默映射**进旧坐标系(§29.7 那个故意接受的代价) |
| 接着关之前那个数, **但驱动器断过电** | 数**证明不了是对的**: 驱动器是开环步进, 没有任何可辨的状态能报出"位置参考已经重来"(§39.7)。屏幕上读着 −75000, 而它可能只是**这套换算**给出的一个数 |
| 读数跟关之前完全对不上 | 这一句**没出现过** —— 说明那份零点没被采纳(量程外 / 轴数变了 / ini 坏了), 走的是"连接即零点"那条路 |

### 15.2 成因与去处

| 最可能是什么 | 为什么 | 处置 |
|---|---|---|
| 「上次那份零点本来就在」(正常) | 关窗时把工作线程手里那份写进了 `bin/scan.ini` | 什么都不用做 |
| 从**别的机器**拷来的 `scan.ini` | 文件跟着程序走, 拷过去就读了 | 认这份坐标系就接着用; 不认就删掉那三个 `zero/*` 键, 或直接删文件(§39.3) |
| 断开期间被人挪过滑台 | 零点记的是**坐标**, 不认物理位置 | 用「设为区域中心」或重新「回零」把它搬回来 |
| 驱动器断过电 | 见上表第三行 | 同上 —— **这一条没有任何自动判据**, 只能靠人看 |

**为什么屏幕句里不给「请……」**: 这里的"要不要动它"完全取决于**现场认不认这个坐标系** ——
接着用是正常用法(不认反而把"重启之后接着扫"这件事弄坏了), 重设也是正常用法。
两种处置的方向相反, 而写哪一条都会把另一半说成错的。所以界面上只说事实。
[`docs/scan_sweep.md`](scan_sweep.md) §39 写的是这一项的设计、代价与实跑清单。

## 16. 限位守卫那三句话 (2026-09-29, `scan` 独有)

这一族是**上位机侧**的一道护栏: 撞到某一侧限位就把当时的位置记下来, 从此那一侧不许再点过去。
它**不是** `607Dh` 软限位(本程序一个字节都不写它), 所以下面每一条的**真实解释权都在上位机这一侧**
—— 驱动器那边什么都不知道。设计、代价与实跑清单在
[`docs/scan_sweep.md`](scan_sweep.md) §43。

### 16.1 界面原话与它们各自说什么

| 界面原话 | 在哪 | 说的是什么 |
|---|---|---|
| `X 轴正限位触发, 已停止; 这一侧已锁住。` | 红色横幅(不自动消失) | **刚刚**撞上, 这一侧从此记下了 |
| `X 轴正限位已锁住, 目标已夹到 13.500 mm。` | 横幅(8 秒自灭) | 你点的那一下被那条线挡了, 走不到你要的位置 |
| `网格越过了限位线: X 轴正限位记在 675000 pul, 网格最远要到 700000 pul。本次扫描未启动。请把区域改小, 或先回零。` | 参数栏红字 + 起扫拒绝 | **这一趟根本起不来** —— 网格里有点在那条线外面 |
| `X 轴正限位区` / `Y 轴负限位区` | 画布, 那条线旁边 | 这是哪一根轴的哪一侧 |
| `X 轴正限位线在面板外 (13.500 mm) —— 那一侧已锁住` | 画布 HUD | 那条线记在 ±16 mm 视野之外, 所以图上看不见它 |

第一句与第二句**不会同时出现**: 第一句是"撞上那一刻", 第二句是"之后又点过去"。

### 16.2 「已停止; 这一侧已锁住」—— 它为什么会出现

| 最可能是什么 | 为什么 | 处置 |
|---|---|---|
| **滑台真的开到了正/负限位开关上** | 手动点击的目标本身就在那一头(画布全域可点, §28), 或点得太靠边 | 这一侧已经锁住了, 往回点是唯一能走的方向。要接着往外走就**先回零**(世代 +1 会让这条线作废) |
| **`2300h` 输入有效电平逻辑配反**(§3.1 那一台) | 那一位一直在, 于是**第一次手动点击**就会被判成撞上 | 见 §3.1。**注意这一条会记下一条错的线**(把当时的位置当成限位), 而那条线在回零之前一直拦着 |
| **`60FDh` 的正/负位接反** | 方向判反 → 线记在**另一侧** | 判据是"正负同时为真就不记"那一条只能挡住最明显的一种。处置同上: 回零让记录作废, 先把接线/取反弄对 |
| 上位机侧「取反」开着而机器是 PNP | 见 §2 / §3.4 | 同上 |

**为什么它不说"撞"**: 限位灯与状态栏那几格说的是"信号此刻有效"(§9 那张表), 而这句横幅是
**动作的后果**(停了、锁了) —— 两件事不一样, 措辞也就不同。

**为什么它可能比那条红横幅早一步**: 这一句的判据是 `6041h` bit11 **或** `60FDh` 的物理开关
**任一为真**(§43.3)。bit11 那条红横幅由 `refreshAxisSignals()` 按它自己的上升沿弹; 极端情况下
物理开关先响而 bit11 还没置起, 那时**只有这一句**会说 —— 少了它就是"滑台自己停了而屏幕上一个
字都没有"。

### 16.3 「目标已夹到 …」—— 点了一下却没走到

**这不是故障**, 是一条**记下来的**限位线在起作用: 你要去的位置在线的外侧, 于是目标被夹到线上
(或者夹到当前位置 —— 若那条线记得比当前位置还靠里)。读数在括号里写着夹到了哪儿。

| 最可能是什么 | 为什么 | 处置 |
|---|---|---|
| 之前撞过这一侧, 线还在 | 记录是"永久"的(用户答复 ①), 一直活到零点世代变 | 往回点是照走的; 要去线外面就**先回零**(世代 +1 → 线作废) |
| 换了工件/挪了滑台, 那条线是上一次的 | 记录记的是**坐标**, 不认物理位置 | 同上 |
| 机器在 `scan` 关着时被**别的程序**回过零 | 世代判据抓得住"经过 scan 的回零", 抓不住"另一个程序单独改过零点"(§43.8 第 2 条) | 同上; 或者删 `bin/scan.ini` 里那五个 `limit/*` 键 |
| 60FDh 读不到(「让 60FDh 进 TxPDO」关着) | 那时**不会记线也不会夹** —— 如果屏幕上出现这句而那个勾是关的, 说明它是**上一次**(勾还开着时)记下的 | 记下的那些线照旧有效; 不然先回零 |

**它为什么总是说"已锁住"而不是"越线了"**: 两种情形(线在外面 / 线在里面)对操作员的含义是
同一件 —— 那一侧现在过不去; 分开说会让人以为有两种不同的状态。

### 16.4 「网格越过了限位线」—— 扫描起不来

**这是一道独立的闸, 与 `validate()` 无关**(§43.6): 参数本身是合法的, 起不来是因为**这一趟的
网格里有几个点在那条线外面**。走一半停会留下一张缺了角的图, 而那个缺口还得靠人看出来 ——
所以它拦在**起点**。

| 最可能是什么 | 为什么 | 处置 |
|---|---|---|
| 区域比记录下来的可用范围大 | 网格最远那个点越过了线, 屏幕上那句里两个数就是它们 | 把区域改小(或把分辨率改大), 让网格落在线内 |
| 那几条边**本来就在限位以内**, 只是线记得太靠里 | 记线时的那一次撞击可能不干净(极性配反、手动推过去蹭了一下), 位置偏内 | 回零一次: 世代 +1 → 整份记录作废 → 起扫这道闸也就不在了 |
| 换过一次工件/夹具, 行程与记线时不一样 | 记录照旧生效 | 同上 |

**这一句里的两个数是有用的**: 「记在 …」是那条线, 「最远要到 …」是网格。两者的差就是得让出
多少 —— 调区域时按这个数改, 不必猜。**出路只写「请把区域改小, 或先回零」**: 那两条是真正
可走的两条路, 别的(改分辨率、改工件)都是它们的具体做法。

### 16.5 「那一侧已锁住」而画布上什么都没有

- 线记在**视野之外**(|位置| > ±16 mm)时图上画不出来, 由 HUD 那一行说它在哪儿(§43.5)。
- 关掉「让 `60FDh` 进 TxPDO」再连: **停照旧会停**(那由 `6041h` bit11 管), 但**记不下方向就
  不记线**, 也就没有线、没有阴影、没有夹取。这不是故障 —— 「什么都不知道时, 敢说的唯一一句
  话是"停", 不是"往那边不许走"」(§43.4)。
